# 17 · 方案自我批判与精简建议（Critical Review）

> 状态：Draft v0.1
> 一份没人批评的方案是不可信的。本文由方案作者自己写，目的是**把"想得太多、做不起"的风险提前暴露**，并给出"资源受限时的降级版本"。

---

## 1. 本方案最容易犯的五个错误（自曝）

### 错误 1：把商业产品 10 年的功能清单当成自己的 18 个月路线图
本方案列出了 8 个能力域、32 项能力。Collibra/Informatica 做到这个广度用了 10 年以上与数百人。**我们的实际产能只有他们的百分之几。**
**修正**：路线图必须按"故事"而非"域"交付（`11` 已这样做，但仍需在立项时二次压缩）。

### 错误 2：低估连接器的长期税
连接器不是"写完就完"，而是**跟随源系统版本来回改**：Hive 升级、Tableau API 变、dbt 版本变、各云厂商 API 折旧。参考开源项目的现实：连接器相关 issue 常年占大头。
**修正**：立项时就要明确"**支持的源系统白名单**"（建议 v1 不超过 10 个），并明确规定"白名单外的源系统由需求方共建"。

### 错误 3：把"治理能力"错当成"治理效果"
平台能提供健康分、待办、记分卡，但**如果组织里没人负责关待办，分数只会变成噪音**。
**修正**：把"域数据管家到岗"作为平台上线的前置条件，而不是上线后的推动事项。

### 错误 4：AI 层设计得比元数据底座还细
`13` 写了完整 Suggestion 模型、provenance、评估集、MCP。这些在**元数据本身覆盖率不到 60% 时毫无意义**（Garbage in, garbage out）。
**修正**：AI 严格排在 Phase 4，且前置条件是"核心资产治理覆盖率 ≥ 60%"。

### 错误 5：策略下发是最高价值，也是最容易延期的一项
`ADR-008` 的策略编译与下发依赖查询引擎/BI 团队的协作、需要灰度与回滚能力，且**错误策略可能造成数据泄露或大面积不可用**。它同时是最高价值与最高风险项。
**修正**：把它作为**独立的先行验证（Spike S4）**，失败则明确降级为"策略导出 + 人工实施"，不要让它拖住整个 Phase 3。

## 2. 可以砍掉/推迟的设计（v1 不需要）

| 设计 | 判断 | 理由 |
|---|---|---|
| 语义/向量混合检索 | 推迟到 P4 | 关键词 + 术语同义词在 v1 已能覆盖 80% 的搜索需求 |
| 数据市场 / 数据产品货架 | 推迟到 P3 | 在目录本身还没被用起来前，货架无人问津 |
| DSAR / 数据主体权利支撑 | 推迟到 P3+ | 强合规行业才需要，先做分级 + 审计 |
| AI 血缘推断 | 建议不做或永远只做建议 | 收益低、污染风险高（ADR-007 的高风险类别） |
| 自研图数据库相关优化 | 不做，除非实测不达标 | 见 `10` 反选型 |
| 多跳（>5）血缘与图算法 | 推迟 | 真实使用中 90% 的查询在 3 跳以内 |
| 移动端 App | 不做（响应式网页 + IM 足够） | 治理动作低频，不需要独立 App |
| 自定义工作流（BPMN） | 不做 | 轻量状态机覆盖 90% 场景 |
| 平台内建报表引擎 | 不做 | 导出到现有 BI 即可 |
| 多语言描述（>2 语言） | 不做 | 中英双语足够 |
| 联邦多租户强隔离 | 按客户需求再做 | 默认逻辑隔离 |
| 数据血缘"实时流式" | 降级为分钟级 | 秒级血缘没有真实消费者 |

## 3. 不可砍的核心（无论资源多紧都要有）

| 必须保留 | 为什么 |
|---|---|
| 统一元数据模型 + 版本审计 | 没有它，后面全是返工 |
| 搜索 + 资产详情页 | 唯一的"每天被用"的入口 |
| 表级血缘（列级可延后） | 治理的核心价值主张之一 |
| 采集的"不覆盖人工 + 可回滚" | 一旦出事就失去信任 |
| 权限与审计（平台内） | 安全底线，不能后补 |
| 协作与通知（IM 集成） | 不进入工作现场 = 没人用 |
| 健康分 + 待办中心 | 治理从"报表"变成"工作"的唯一手段 |

## 4. 三种资源档位下的降级方案

### 档位 A：1 人 · 3 个月（"别自研"）
**建议：不要自研。** 直接用 OpenMetadata（Docker 起、配 5 个连接器、开血缘），把力气花在组织推行与标准制定上。
治理平台的瓶颈在这个阶段不是软件，而是**没人负责治理**。

### 档位 B：2–3 人 · 6 个月（"最小自研内核"）
只做四件事：
1. 统一元数据模型 + 采集框架 + **5 个连接器**（MySQL/PG/Hive/Trino/dbt）；
2. 搜索 + 资产详情页 + Owner/标签/描述（含来源与审计）；
3. 表级血缘（列级仅对 dbt/SQL 主路径）+ 影响分析（3 跳）；
4. 待办中心 + 钉钉/飞书通知。
**不做**：质量引擎、契约、策略下发、AI、图库、多租户强隔离。
> 这个档位的产出是"一个很好用的目录"，价值真实但天花板明显。

### 档位 C：4–6 人 · 18 个月（本方案）
按 `11-roadmap-mvp.md` 的 Phase 0–4 推进，并在 Phase 3 交付策略下发（差异化核心）。

**决策规则**：先诚实评估自己能稳定拿到哪个档位，再决定"自研 / 二开 / 采购"（见 `12` 第一部分）。

## 5. 对"是否应该自研"的最强反驳（应当被正面回答）

**反驳一**：开源已经免费且够好，为什么不用？
→ 回答：如果诉求止于"搜索 + 血缘 + 基础质量"，**应该用开源**。自研的唯一正当理由是"数据面策略执行 + 深度定制 + 长期可控"。若这三条都不成立，本方案不成立。

**反驳二**：自研 3 年也追不上开源社区的连接器广度。
→ 回答：同意，**不该追**。策略是复用开源连接器（Apache-2.0 允许）、限制白名单、只保证"核心源系统的一流体验"。

**反驳三**：治理平台的失败率极高，为什么要自己造一个很可能没人用的东西？
→ 回答：**失败原因是组织而非软件**。所以本方案把"待办中心 / IM 集成 / 域记分卡 / 采用度 KPI"放在核心位置，并在 `11` §5 预设了退出条件（周活 < 20% 即停止新功能）。

**反驳四**：AI 时代还需要人填元数据吗？
→ 回答：AI 降低了填的成本，但**提高了对"元数据可信度"的要求**（因为 AI/Agent 会直接消费它）。所以本方案强调 provenance 与人工确认，而不是让 AI 大量自动写入。

**反驳五**：为什么不用图数据库？血缘不就是图吗？
→ 回答：是图，但 90% 的查询是 1–3 跳。用 PG 边表 + 物化闭包能满足 SLO，且省掉一个分布式存储的运维。**这是"够用即最优"的取舍，不是能力缺失**（若 Spike S2 证伪，方案已预留派生图库路径）。

**反驳六**：OpenMetadata + Elementary 都是免费可自托管的，组合起来就能覆盖"目录 + 血缘 + 质量"，为什么还要自研？
→ 回答：这是**最有力的反驳**。`research/03` §7.8 的结论是：如果自研平台在"目录 + 质量"范围内**无法显著超过**"Elementary + OpenMetadata 组合"，那么立项理由就只剩两块：
① **D7 访问治理与策略执行**（策略编译下发到数据面：开源不做，商业侧仅少数做到闭环）；
② **D8 治理运营闭环**（健康分 / 待办 / 记分卡 / 采纳度：开源止于覆盖率统计）。
如果这两块在你的场景中也不重要，**正确动作是二开（或直接用），不是自研**。本方案不回避这个结论，并把它写进了 `12` 的退出条件。

**反驳七**：国内客户几乎不会为"纯目录产品"单独买单。
→ 回答：同意（`research/03` §7.9）。国内政企/金融买的是"生产链路"（集成—开发—调度—质量—安全 同平台）。但自研**不该去造开发 IDE**（那是 DataWorks/DataPHin 的战场，且重）。差异化的正确切口是**治理动作的自动化率**：自动识别、自动推荐规则、自动生成口径、自动派单——用最少的人力把治理做起来。

## 6. 需要立即修正/关注的三件事

1. **把 Spike（`15`）作为立项前置**：S1（血缘解析）与 S2（PG 血缘性能）若同时不成立，整个方案的技术基础动摇。
2. **把"域数据管家到岗"写成项目前置条件**：否则做出来没人用。
3. **在方案评审时明确"支持源系统白名单"与"不做清单"**：这两份清单是防止范围蔓延的最有效工具。
