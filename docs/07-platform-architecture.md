## 1. 设计立场（Design Stance）

自研通用数据治理平台，最容易失败的方式是"照着 Collibra 的功能清单做一个更便宜的山寨版"——那会得到一个功能很多、每项都不够好的东西。本方案取相反的立场：

**不做功能全集，做元数据内核 + 治理闭环 + 开放能力。**

具体六条立场，后面所有设计都从这六条推导：

| # | 立场 | 反面（我们不做什么） | 来源启发 |
|---|---|---|---|
| S1 | **元数据是产品，不是文档**：元数据要被下游系统消费（CI、查询引擎、BI、IDE、AI Agent），而不是只给人看 | 只做一个查询用的目录 UI | Alation/Atlan 的 "active metadata"、Informatica CLAIRE |
| S2 | **单一真相源 + 可重建派生视图**：一切元数据变更进 append-only 事件流，图/搜索/宽表都是派生视图，可重放重建 | 图数据库、搜索引擎、关系库三处平级写入（DataHub 式运维负担） | DataHub 的事件驱动优点 + 其双写一致性痛点 |
| S3 | **治理即代码**：契约、策略、质量规则、术语都能 Git 管理，走 CI 门禁，变更带血缘影响的 PR 检查 | 只能在 UI 上点配置、无法版本化 | Datafold 的 CI diff、dbt 的 as-code 文化 |
| S4 | **联邦治理，中心供能**：Domain / Data Product 是一等公民，中心平台提供能力与度量，域负责自己资产的文档、质量与 SLO | 中心团队替所有域维护元数据（必然烂尾） | Data Mesh 的 federated computational governance |
| S5 | **AI 产出必须可审计**：AI 生成的描述/标签/血缘都是"建议 + 置信度 + 来源"，需人工确认才生效，绝不静默写入 | 让 LLM 直接写元数据 | Monte Carlo 的置信度思想、Gartner 2025 对 AI 元数据的治理要求 |
| S6 | **开放标准优先，避免锁定**：对外用 OpenLineage / ODCS / Iceberg REST / MCP 等标准，对内模型可扩展 | 自定义协议、私有格式 | OpenLineage 生态、Gravitino 的联邦思路 |

## 3. 逻辑架构（Logical Architecture）

分五层 + 两条贯通纵轴。分层的关键约束是**依赖单向向下**：上层可以调用下层，下层永不反向依赖上层。

```
┌──────────────────────────────────────────────────────────────────────────────┐
│ L5 体验与开放层  Experience & Open Surface                                     │
│  Web UI │ 数据资产门户 │ CLI │ SDK(Py/Java/Go) │ GraphQL/REST │ Webhook       │
│  Embedded Widget(BI/IDE) │ MCP Server │ CI 插件(GitHub/GitLab/Jenkins)        │
├──────────────────────────────────────────────────────────────────────────────┤
│ L4 治理能力层  Governance Capabilities（可独立演进的领域服务）                    │
│  Glossary │ Quality & Observability │ Contract │ Classification │ Policy      │
│  Access Request │ Scorecard │ AI Copilot(建议引擎)                            │
├──────────────────────────────────────────────────────────────────────────────┤
│ L3 元数据核心层  Metadata Core（平台的"真相源"，最稳定的一层）                     │
│  Model Registry(实体/方面/关系定义) │ Entity Service │ Aspect Store(版本化)     │
│  Lineage Service(边 + 置信度) │ Graph Query │ Semantic Service │ Audit Trail   │
├──────────────────────────────────────────────────────────────────────────────┤
│ L2 索引与派生视图层  Derived Views（全部可从事件流重建，可丢弃）                   │
│  Search Index(OpenSearch) │ Vector Index │ Lineage Cache/闭包 │ OLAP 宽表       │
│  Feed/Timeline │ 统计聚合(用量/人气)                                          │
├──────────────────────────────────────────────────────────────────────────────┤
│ L1 接入层  Ingestion & Integration                                             │
│  拉模式：Connector Runtime + Collector Agents(部署在数据侧)                     │
│  推模式：Events API(OpenLineage 兼容) │ SDK 埋点 │ Webhook 回传                 │
│  外部目录联邦：Iceberg REST / Glue / Unity / Hive Metastore / Gravitino        │
└──────────────────────────────────────────────────────────────────────────────┘
   ┌─ 纵轴 A：平台基座 ─────────────┐   ┌─ 纵轴 B：治理与运维 ──────────────┐
   │ 多租户 │ 身份与 SSO │ 密钥管理   │   │ 可观测性(Trace/Metric/Log)        │
   │ 调度器 │ 工作流引擎 │ 通知中心   │   │ 数据分级与自身合规 │ 容量与成本    │
   │ 事件总线(Kafka/PG) │ 配置中心    │   │ 备份恢复 │ 升级与迁移 │ 灰度发布   │
   └───────────────────────────────┘   └──────────────────────────────────┘
```

### 3.1 为什么 L3 是"核心"而 L2 是"派生"

这是本架构与 DataHub（Neo4j + Elasticsearch + RDBMS 三处写）最重要的区别。

- **真相源**只有一处：PostgreSQL 中的 `entity` / `aspect`（JSONB，带版本） / `edge`（血缘等关系）。
- **事件流**记录每次变更（`MetadataChangeLog`），是"真相源的可重放日志"。
- **派生视图**（搜索索引、向量索引、血缘闭包缓存、统计宽表、Feed）全部由消费者从事件流构建：
  - 索引损坏 → 重置 offset 重放，无需从业务系统重新采集；
  - 新增一种检索视图（例如未来加图数据库或向量库）→ 加一个消费者，不动核心；
  - 一致性语义清晰：派生视图允许最终一致，且带 `indexed_watermark` 让 UI 能显示"元数据已更新，索引同步中"。

这直接解决三个现实痛点：索引与元数据不一致导致"搜不到刚建的资产"、升级时索引重建停机、多存储写入的事务边界撕裂。

### 3.2 血缘为什么不默认上图数据库

DataHub 用 Neo4j（后改为图索引抽象）承载血缘，带来真实的运维成本。我们的替代方案：

| 阶段 | 数据规模 | 方案 | 理由 |
|---|---|---|---|
| v1 | 节点 < 100 万，边 < 500 万 | PostgreSQL 边表 + `WITH RECURSIVE` + 邻接表索引；对高频查询物化 3 跳以内闭包 | 单库运维，事务一致，够用 |
| v2（**仅当超出 v1 适用范围时启用**） | 节点 + 边 > 1 亿，或需 ≥4 跳交互式遍历，或需图算法 | 引入图存储作为**派生视图**（NebulaGraph / HugeGraph，**不推荐 JanusGraph**——深多跳退化最明显），从边表同步 | 只读派生，不承担真相源职责，坏了可丢 |
| 任何时候 | 影响分析（上游 N 跳、下游爆炸半径） | 预先物化"关键路径"与"域级聚合图" | 90% 查询只关心 1–3 跳，物化即够 |

> ### 规模口径（唯一权威定义）
>
> `19` 独立评审 **B1** 指出：本方案此前在不同文档里对"规模"给出了互斥的表述（`07` §3.2 说 v1 是"节点 < 100 万/边 < 500 万"，而 `07` §8 与 `11` Phase 3 却用"千万实体/亿级边"做 SLO 验证），按方案自己的规则（`09` §9.2 的"节点+边 > 1 亿即触发图库"）v1 已经越界。**以下为唯一口径，其它文档一律以此为准：**
>
> | 口径 | 数字 | 含义 |
> |---|---|---|
> | **v1 设计适用范围** | **≤ 500 万实体、≤ 5000 万血缘边** | PG 边表 + 递归查询 + 有界闭包（depth ≤ 3）**必须在此范围内**满足 §8 的 SLO |
> | **SLO 验证规模** | 与设计适用范围一致；另跑 **2 倍压力档** | 压测不得用超出适用范围一个数量级的规模去"证明"能力（那是虚假信心） |
> | **溢出触发点** | 节点 + 边 **> 1 亿** | 达到即**必须**引入派生图库（上表的 v2 方案）——这不再是"可选优化"，而是**适用范围边界** |
>
> **推论（必须由业务方拍板）**：若预期一开始就在亿级边量级，则派生图库要进 **v1** 交付清单，工期与运维成本相应上升；若预期在 5000 万边以内，v1 的 PG 方案成立。**Spike S2 必须同时产出"1–3 跳闭包在真实宽扇出拓扑下的行数与刷新耗时"**（`10` §3.1 此前只估了 Aspect 容量，漏估了闭包表）。

配套设计（这是"血缘可信度"的关键）：
- 每条边带 `source`（`sql_parse` / `openlineage` / `query_log` / `bi_api` / `manual`）、`confidence`（0–1）、`job_id`/`run_id`、`first_seen`/`last_seen`、`observed_count`。
- 同一条边多来源命中 → 置信度提升、来源合并展示。
- 长期未观测（超过 N 个调度周期）→ 标记 `stale`，UI 弱化显示，不静默保留幽灵血缘。
- 解析失败/低置信 → 进"待确认血缘"工作队列，由域负责人确认（把不确定显性化，而不是假装准确）。

## 4. 运行时架构（Runtime / 部署形态）

三种形态，同一套代码，靠配置与模块开关区分，**不做多套产品**：

| 形态 | 面向 | 组成 | 说明 |
|---|---|---|---|
| **单机版 / Dev** | 开发、POC、小团队 | 1 容器组：API + Worker + PG + OpenSearch（可选内嵌）+ UI | `docker compose up` 一条命令起 |
| **标准版 / 生产** | 中型企业 | API(无状态 ×N) + Worker(采集/质量/AI 异步任务 ×N) + PG(主从) + OpenSearch + Kafka/Redpanda + Redis + 对象存储 | Helm 部署，水平扩展点主要在 Worker |
| **联邦版 / 集团** | 多地域、多 BU、数据不出域 | 中心控制面 + 每域/每地域一个 **Edge Agent**（采集与本地缓存，仅上报元数据与统计摘要，不上报数据样本）+ 只读缓存节点 | 对应"数据不出域，元数据可汇聚" |

关键工程决策：
- **控制平面与数据平面分离**：平台自身**不存储、不中转业务数据**；仅在用户显式开启时对数据做**采样剖析**（采样结果与统计量落元数据库，原始样本不持久化或短期加密存储 + 可配置关闭）。
- **采集位置可插拔**：Agent（推）与 Server（拉）两种模式并存。多网络域/私有子网只能是 Agent 推模式——这是企业落地的硬约束，必须 v1 就支持，不能像很多开源项目那样默认 Server 拉。
- **模块化单体优先**：v1 是一个可水平扩展的模块化单体（modular monolith），按 L3/L4 划分清晰模块边界与内部 API；只有当某个模块出现独立扩缩容需求（典型：血缘解析、AI、质量执行）才拆成独立服务。**反对一开始微服务化**——治理平台的流量特征（读多、突发、长尾 connector）用微服务换不来收益，只会换来分布式事务与调试地狱。

## 5. 关键数据流（Key Flows）

### 5.1 采集 → 目录可见（Pull 模式）
```
Scheduler 触发 Collection 任务(schedule/cron)
  → Connector 从源系统读取元数据(information_schema / HMS / BI API / …)
  → 标准化为统一模型 Entity + Aspect(平台无关)
  → 与上次快照 diff（stateful ingestion）→ 生成 MetadataChangeProposal 列表
  → 提交到 Metadata Core（校验 → 写 aspect 版本 → 追加事件）
  → 事件消费者：Search Indexer / Lineage Builder / Stats Aggregator / Webhook Dispatcher
  → UI 可搜可见（索引 watermark 同步后）
```
要点：**增量 + diff 驱动**，只有真变更才产生事件；每次采集带 `run` 记录（新增/更新/删除/失败数），采集健康本身也是被治理的对象。

### 5.2 血缘产生（四路汇聚）
```
① 静态解析：SQL / dbt manifest / Spark 逻辑计划 → sqlglot 列级解析 → 候选边(confidence~0.8)
② 运行时上报：作业 OpenLineage 事件 → 作业级/数据集级边(confidence~0.95)
③ 查询日志挖掘：BI/查询引擎历史 → 读写关系 + 表联查(join)关系 + 使用热度(confidence~0.7)
④ 人工/BI API：报表字段映射、人工补录(confidence~1.0，标记为人工)
  → 血缘合并器（去重、置信度融合、冲突标记）
  → 写 edge + 事件 → 血缘索引刷新 → 影响分析 / 健康分 / 告警可用
```

### 5.3 契约与质量门禁（CI 闭环）
```
开发者改 model / DDL → PR
  → CI 插件调用平台：
      · Schema 兼容性检查（对照已注册契约）
      → 血缘影响分析（这个列的消费者是谁？谁会 break？）
      → 质量规则必填检查（新表是否定义了 owner/分级/契约？）
  → 结论回写 PR（评论 + check status）：阻断 / 警告 / 通过
  → 合并后：契约版本入注册表，触发下游订阅者通知与影响面走查任务
```

### 5.4 访问申请与策略下发
```
用户在某资产上点"申请访问" → 自动带出资产分类分级 + 用途 + 期限
  → 按策略路由到 Owner/数据管家审批（工作流引擎）
  → 批准 → 策略记录产生 → 策略编译器生成下游可执行产物：
       · Trino/Spark：行过滤 / 列掩码 SQL 表达式
       · BI/SDK：标签与可见性规则
       · 计算引擎侧缓存刷新（TTL/推送）
  → 到期自动回收 + 审计留痕 + 定期最小权限复盘建议
```

### 5.5 AI 建议闭环
```
触发（新建资产 / 用户提问 / 定时扫描 / 契约变更）
  → 构建上下文（schema、采样统计、血缘邻居、术语表、已有描述、相似资产）
  → LLM 生成候选（描述 / 标签 / 分类 / 术语映射 / 血缘推断）
  → 写为 Suggestion 实体（含 provenance：模型、prompt 版本、证据引用、置信度）
  → UI "建议收件箱" → 人工接受/修改/拒绝（反馈用于评估与阈值调优）
  → 接受后才写入正式元数据，并记录 accepted_by / accepted_at
```

## 6. 与主流开源平台的结构性对比

结构化对比表（详细功能对比见 `06-competitive-synthesis.md`）：

| 维度 | OpenMetadata | DataHub | Apache Atlas | 本方案 |
|---|---|---|---|---|
| 元数据模型 | 单一 JSON-Schema 驱动实体模型 | Entity + Aspect + URN，PDL 代码生成 | TypeSystem（类型+关系+图） | **Entity + Aspect + Edge，模型注册表驱动 + 代码生成** |
| 变更传播 | API 写库 + 索引 | Kafka MCE/MAE/MCL 事件流 | Kafka + Hook | **PG 真相源 + 事件流 + 全部派生视图可重放重建** |
| 图存储 | 关系表（元数据库）内表达关系 | 图索引（抽象可插拔） | JanusGraph/HBase 重依赖 | **v1 PG 边表+递归查询，图库仅作可选派生视图** |
| 血缘 | SQL 解析 + 集成，表/列级 | 跨平台聚合强，多来源 | Hook + 解析，较旧 | **四路汇聚 + 置信度/来源/新鲜度显性化** |
| 契约 | 内置 Data Contract | 有 Contract/Assertion（云版更强） | 弱 | **ODCS 兼容 + CI 门禁 + 生产者消费者关系（一等公民）** |
| 策略执行 | RBAC/策略，偏平台内 | 策略在平台内为主 | 平台内 | **策略编译下发到查询引擎/BI（active policy）** |
| 采集部署 | Server 拉为主 | 拉 + 部分推 | Hook 深度绑定 Hadoop | **Pull + Edge Agent 推，v1 即支持离线/隔离域** |
| AI | 助手 + 搜索增强 | 云版 AI | 无 | **Suggestion 实体 + provenance + 人工确认闭环（可审计）** |
| 部署复杂度 | 低 | 高（Kafka/图/ES） | 高（Hadoop 系） | **单机 compose / 标准 Helm / 联邦，同一套代码** |
| 扩展方式 | 改源码 / 插件 | 自定义 aspect（较重但强） | 自定义 Type | **模型注册表 + 扩展包（connector/规则/AI 技能）+ 单二进制热加载** |

**结论性定位**：本方案 = OpenMetadata 的"开箱可用 + 一体化模型" + DataHub 的"事件驱动与可扩展性" + 商业产品的"策略执行与治理运营" − 三者各自的运维地狱。

## 7. 明确不做什么（Non-Goals）

写清楚 Non-Goals 是这份架构最重要的部分之一：

1. **不做 ETL/调度平台**：不与 Airflow/DolphinScheduler 竞争，只做集成与血缘采集。
2. **不做 BI/查询引擎**：不做报表、不做查询执行（策略编译产物交给 Trino/Spark 执行）。
3. **不做主数据管理（MDM）**：v1 只做术语表与业务语义映射，不做黄金记录合并与分发。
4. **不接管业务数据存储**：不做数据湖/数仓的存储层。
5. **不做通用数据交换/共享市场交易能力**：数据产品货架仅做"发现与申请"，不做计费结算。
6. **不做通用工作流引擎**：审批流基于成熟引擎（Temporal/Camunda/自研轻量状态机），不自研 BPMN 平台。
7. **不在 v1 做跨租户数据融合与联邦查询**。

## 8. 架构质量属性与目标（SLO）

平台自身也要有 SLO，否则"治理别人的平台自己不可用"是最大的信任崩塌：

| 属性 | 目标 | 验证方式 |
|---|---|---|
| 可用性 | 元数据读取 99.9%；采集任务不阻塞前台 | 混沌测试 + 采集队列隔离 |
| 读延迟 | 资产详情 P95 < 300ms；搜索 P95 < 500ms | 压测（**v1 设计适用范围**：500 万实体 / 5000 万边，见 §3.2「规模口径」；另跑 2 倍压力档） |
| 写吞吐 | 元数据事件 ≥ 5k/s 峰值（大批量采集） | 批量导入压测 |
| 血缘查询 | 3 跳内影响分析 P95 < 1s（**在 5000 万边规模下**） | 基准数据集（见 §3.2「规模口径」） |
| 一致性 | 真相源强一致；派生视图最终一致（watermark 可见） | 一致性校验任务（对账） |
| 可恢复 | 索引全量重建 < 2h（**500 万实体规模**）；RPO ≤ 5min | 恢复演练 |
| 可扩展 | 新增一个 connector 不改核心代码；新增 aspect 不破坏旧客户端 | 契约测试（消费者驱动） |

> **规模口径说明**：本表所有数字均以 §3.2 定义的"**v1 设计适用范围**（500 万实体 / 5000 万边）"为准。此前版本的"千万实体 / 亿级边"表述与 §3.2 冲突，已按 `19` 独立评审 B1 修正——**SLO 必须在方案声明的适用范围内被验证，否则等于没有 SLO**。超出适用范围时的路径（派生图库进 v1）见 §3.2。

## 9. 待决策项（Open Questions）

这些问题需要在方案评审时由业务侧拍板，架构上先保留可切换设计：

1. **自研 vs 二开的最终边界**（详见 `12-build-vs-extend-and-adr.md`）：内核自研、连接器复用开源的混合路线是否被接受？
2. **技术栈主语言**：Java/Kotlin（生态最顺、可复用 OM/DataHub 生态）vs Go（运维轻）vs Python 优先（解析与 AI 顺）。方案默认 **Java/Kotlin 控制面 + Python 解析/AI 侧车 + Go Agent**。
3. **多租户语义**：是"一套平台多业务域（逻辑隔离）"还是"多法人/多租户强隔离（含元数据不互见）"？影响权限模型与部署拓扑。
4. **是否要求元数据自身国产化/信创适配**（数据库、OS、CPU 架构），影响中间件选型。
5. **AI 是否允许调用外部 LLM API**（合规与数据出境），决定是否需要私有化模型与本地向量库。
6. **首要痛点排序**：目录发现 / 血缘 / 质量 / 合规，哪个是业务方最痛？决定 MVP 侧重（本方案默认以"目录 + 血缘"切入）。
