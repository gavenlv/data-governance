# 13 · AI 原生治理层设计（AI-Native Governance Layer）

> 状态：Draft v0.1
> 立场：**AI 是治理的"放大器"与"降低门槛的手段"，不是治理的替代品。任何 AI 产出都必须可追溯、可驳回、可度量。**

---

## 1. 场景盘点：按"成熟度 × 价值"排序

| # | 场景 | 价值 | 技术成熟度 | 风险 | 交付阶段 |
|---|---|---|---|---|---|
| A1 | 自然语言搜索与问答（"找订单相关的表"、"GMV 口径是什么"） | 高（降低发现门槛） | 高 | 中（幻觉、越权） | Phase 4（MVP 可做纯检索版） |
| A2 | 自动生成描述（列/表）与业务别名 | 高（最耗人力的治理动作就是写描述） | 高 | 中（质量参差） | Phase 4 |
| A3 | 自动打标/分类建议（PII、主题域、敏感度） | 高（合规刚需） | 中高 | 高（误判导致漏保护） | Phase 1 用规则，Phase 4 加模型 |
| A4 | 术语/同义词映射建议（把列映射到业务术语） | 中高（打通业务语言） | 中 | 中 | Phase 4 |
| A5 | 血缘推断（从 ETL 代码/文档/命名推断关系，补全静态解析的盲区） | 中 | 中低 | 高（错误血缘污染全图） | Phase 4，仅作"待确认建议" |
| A6 | 治理 Copilot（"给我这个域的治理待办清单并按影响排序"） | 中高（把运营自动化） | 中 | 中 | Phase 4+ |
| A7 | 智能变更影响面摘要（PR 里自然语言说明影响） | 中 | 高 | 低 | Phase 2 |
| A8 | 质量规则建议（根据剖析结果与历史故障推荐规则） | 中 | 中 | 中 | Phase 3+ |
| A9 | 数据访问申请的智能路由与风险评分 | 中 | 中 | 中高（安全相关） | Phase 3+ |

**排序原则**：先做"降低人力成本、错了也不致灾"的（A1/A2/A7），后做"错了会致灾"的（A3/A5/A9）——后者必须带人工确认与保守默认值。

### 1.1 一条前置判断：AI 问答必须基于语义层，而不是裸 SQL

来自 `research/04` §6 的实证结论（基准已换代，**数字口径已按 `19` 独立评审事实项 5 校正**）：**Spider 1.0 已被刷满、无区分度；Spider 2.0（真实企业级、多方言、长上下文，arXiv:2411.07763）的成功率显著低于 Spider 1.0；BIRD（真实脏数据 + 外部知识）上 SOTA 约在 70% 量级且随难度分层大幅下降。另一项需继承的免责：现有 text-to-SQL 基准本身存在标注错误问题，因此"某个百分比"不应作为承诺。** 结论不变——**单靠"把 schema 喂给 LLM"不足以面向业务。**

因此本方案的两条硬性设计：

1. **语义层是一等公民**：指标定义、维度、口径公式、join 关系、同义词作为**独立实体 + 版本化 + 挂接血缘**，而不是某个 BI 工具的附属配置。它是 AI 的 grounding，也是"GMV 口径是什么"这类问题的唯一正确答案来源。
2. **默认"生成语义层查询"，而不是"生成裸 SQL"**：自然语言入口先落到受治理的指标/维度上，再由语义层负责翻译成 SQL。这样既提升准确率，也天然继承了语义层里的权限与口径约束。

> 这条判断也解释了为什么"接入 dbt Semantic Layer / Cube / Apache Ossie"被列入路线图 P4（`09` §9.10、`11`）：**没有语义层，AI 问答的准确率天花板很低，做了也是摆设。**

## 2. AI 层架构

> ⚠️ **v1 范围声明（采纳 `19` 评审过度设计项 3）**：本节及其 §2.1 的上下文块设计、reranker、向量检索等**全部属于 P4 范围**——`17` §2 的"可砍清单"已把语义/向量混合检索推迟到 P4。**v1 不实现本节任何组件**；在此保留设计是为了避免 P4 时重新推导（尤其"上下文按权限裁剪"与"版本戳随输出存档"这两条约束，晚做会返工）。**AI 的前置条件是核心资产治理覆盖率 ≥ 60%**（`17` §1 错误 4），覆盖率不到就做 AI 等于放大器放大垃圾。

```
┌─────────────────────────── 请求入口 ───────────────────────────┐
│ Web 问答框 │ 建议收件箱 │ 定时扫描任务 │ CI 评论 │ MCP/Agent 调用  │
└──────────────────────────────┬────────────────────────────────┘
                               ▼
┌──────────────────── AI 编排层 (Orchestrator) ────────────────────┐
│ 意图识别 → 任务路由(检索/生成/推理/多步) → 上下文构建 → 模型调用   │
│ 权限裁剪 │ 敏感过滤 │ 缓存 │ 配额与降级 │ 审计 │ 评估埋点          │
└───┬───────────────┬───────────────┬───────────────┬────────────┘
    ▼               ▼               ▼               ▼
 检索服务        上下文组装        模型网关        Suggestion 服务
(混合检索+rerank) (血缘/术语/统计) (路由/多模型)   (建议实体+闭环)
    │               │               │               │
 OpenSearch      Metadata Core   LLM API /       Metadata Core
 +向量索引       Lineage/Glossary  私有模型       (with provenance)
```

### 2.1 上下文构建（RAG 的元数据特化）
不把"整个目录"塞给模型，而是**按任务动态组装最小充分上下文**：

| 上下文块 | 内容 | 用途 |
|---|---|---|
| 资产骨架 | URN、类型、平台、schema、分级、Owner | 几乎所有任务 |
| 血缘邻域 | 1–2 跳上下游（表级为主，列级按需） | 影响分析、根因、血缘推断 |
| 语义邻域 | 命中的术语、同义词、指标定义 | 问答、术语映射 |
| 统计画像 | 行数、空值率、Top-K 值、样例格式（脱敏） | 描述生成、分类 |
| 人类已有知识 | 已有描述、文档、评论、历史建议与是否被采纳 | 提升一致性（少"重新发明"） |
| 相似资产 | 向量近邻（跨库的同名/同构表） | 描述迁移、术语映射 |
| 证据引用 | 每条上下文的来源（URN + aspect + 版本） | 输出引用与可审计 |

**关键实现点**：
- 上下文本身要**按调用者权限裁剪**（见 §4），而不是生成后再过滤。
- 上下文带**版本戳**，模型输出与上下文一起存档，便于事后复现"它当时看到了什么"。
- 长上下文成本控制：先检索后精排，只把 Top-K（默认 20–50 个块）交给模型。

### 2.2 模型网关（Model Gateway）
- 多模型路由：小模型跑高频低成本任务（分类、别名生成），大模型跑推理与问答。
- 统一抽象（OpenAI 兼容协议 + 云厂商适配），支持**私有化模型**（合规要求场景）。
- 能力：配额、速率限制、重试与超时、降级（模型不可用时回退规则/检索）、prompt 版本管理、结果缓存（同上下文哈希命中直接复用，省成本且保证一致性）。
- 全量审计：每次调用记录（任务、调用者、模型、prompt 版本、token 数、成本、耗时、是否被采纳）。

## 3. Suggestion 实体：AI 写入元数据的唯一合法通道

**铁律：AI 永远不直接写正式元数据。** 一切 AI 产出先落为 `Suggestion`，人工接受后才写 Aspect。

```json
{
  "suggestionId": "sug_01H...",
  "targetUrn": "urn:dg:dataset:prod.hive.dw.dim_customer",
  "aspectType": "descriptions",
  "proposedValue": { "zh": "客户维度表，每行一个客户，SCD2 保留历史版本" },
  "kind": "AI_GENERATED",
  "provenance": {
    "task": "generate_description",
    "model": "internal-llm-v3",
    "promptVersion": "desc-gen@1.4",
    "contextRefs": ["urn:dg:dataset:...ods_customer#schema", "urn:dg:glossaryTerm:crm.customer", "urn:dg:dataset:...dim_customer#qualityProfile"],
    "contextHash": "sha256:...",
    "generatedAt": "2025-06-01T10:00:00Z"
  },
  "confidence": 0.78,
  "riskLevel": "LOW",
  "state": "PENDING",              // PENDING | ACCEPTED | EDITED | REJECTED | EXPIRED | AUTO_APPLIED
  "reviewer": null,
  "decidedAt": null,
  "feedbackReason": null           // 拒绝原因，用于评估与 prompt 改进
}
```

配套机制：
- **Suggestion 收件箱**：按风险/收益/置信度排序，支持批量接受；每条展示"证据引用"（点开可看它依据了哪些元数据）。
- **自动应用策略（谨慎）**：仅允许低风险项自动应用（例如"从相似表补全列描述"这类纯冗余信息），且必须：① 可一键全局回滚（按批次）；② UI 标记为 `AI`（与人工内容视觉区分）；③ 阈值与类别白名单可配置，默认关闭。
- **评估闭环**：采纳率 / 编辑率 / 拒绝率 按任务与模型版本统计；拒绝原因回灌到 prompt 与评估集。

## 4. 权限与安全（AI 场景下最容易出事的地方）

| 风险 | 对策 |
|---|---|
| **越权泄露**：用户通过问答问到无权访问的资产信息 | **检索前置授权过滤**（在向量库/ES 查询层注入"可见资源"过滤，**绝不能"先取结果再过滤"**——那已经把内容放进上下文了）；与搜索共用同一套授权判定；**向量索引按租户隔离**；生成后做二次校验（输出中出现的每个 URN 都要过权限检查，不通过则剔除并说明"存在无权访问的相关资产"）；**测试用例必须包含越权探测**（安全测试的一等公民）；LLM 网关记录"用户 → prompt → 引用资源"以满足审计 |
| **PII 进入 LLM** | 上下文中的采样值与自由文本列做检测与替换（如 `PHONE_1`），或按分级直接排除；外部 LLM 调用默认禁用高敏资产上下文，可用配置强制 |
| **Prompt 注入**：元数据内容（描述、注释、文档）里藏指令 | 元数据一律视为不可信输入（**表描述、列注释、样本值都是用户可控内容**），放入明确分隔的"数据区"并做转义/隔离；系统指令不可被数据区覆盖；工具返回结果不得被当作指令执行；**输出侧强校验**（若生成查询：只读、表白名单、行数上限、超时）；对输出做动作权限校验（模型不能"决定"执行写操作） |
| **幻觉引用** | 强制引用格式（回答中每个事实后附 URN）；引用必须由服务端校验存在性，无效引用直接标红/删除 |
| **成本失控** | 配额（用户/租户/任务维度）、缓存（**同输入指纹不重算**）、上下文裁剪、小模型优先（本地小模型做分类/摘要，大模型只做难例）、批量任务限速、成本看板与告警。**基准量级**：若按"表 × 列 × 每日刷新"全量生成描述，成本可达数千美元/月（`research/04` 工程经验值）→ 因此**只对"新增 / 变更 / 高价值"实体生成** |
| **供应商侧数据留存** | 外部 LLM 必须选**承诺零数据保留 / 不用于训练**的服务，并在合同与技术两侧同时要求（参考：Alation Agent Studio 以 **Zero Data 架构**承诺第三方 LLM 侧不留数据，`research/03` §2.2）。**平台自身的审计日志只记录"谁问了哪类资产、命中了哪些 URN"，不记录 prompt 原文中的敏感值**——否则审计日志本身成为泄漏源 |
| **模型/供应商锁定** | 网关抽象 + prompt 与评估集自持；关键任务保持"无 AI 也能用"的降级路径 |
| **审计与合规** | 每次 AI 调用与每次建议的接受/拒绝全部入审计日志；可回答"这个描述是谁写的、依据什么、谁批的" |

## 5. 质量评估（没有评估就没有 AI 能力）

| 层 | 方法 |
|---|---|
| 离线评估集 | 自建金标准：200–500 条"问题 → 期望资产/期望答案要点"，覆盖中文、缩写、别名、跨域 |
| 任务级指标 | 检索 Recall@10 / nDCG；描述生成用人工评分 + 接受率；分类用 P/R/F1（**漏判比误判更危险**，优先高召回） |
| 在线指标 | 采纳率、编辑率、追问率、无结果率、越权拦截次数、单位成本 |
| 回归测试 | prompt/模型变更必须跑评估集（CI 门禁，低于基线阻断） |
| 对抗测试 | 越权提问、注入攻击、诱导生成敏感内容，纳入安全测试用例库 |

## 6. MCP / Agent 接口设计

外部 AI Agent（IDE 助手、BI 助手、企业内部 Copilot）通过标准协议访问治理能力。设计要点：

| 工具（Tool） | 说明 | 授权 |
|---|---|---|
| `search_assets(query, filters)` | 搜索资产（结果按调用者权限过滤） | 读 |
| `get_asset(urn)` | 资产详情（描述/schema/Owner/分级） | 读（分级受限字段裁剪） |
| `get_lineage(urn, direction, depth)` | 血缘（含置信度与来源） | 读 |
| `get_glossary(term)` | 术语与指标口径 | 读 |
| `get_quality(urn)` | 质量结果与 SLO | 读 |
| `check_contract(urn, proposedSchema)` | 契约兼容性检查 | 读 |
| `propose_update(urn, aspect, value)` | 提交建议（**不是直接写**） | 建议权（走 Suggestion 流程） |
| `request_access(urn, purpose, ttl)` | 发起访问申请 | 申请权（走审批流） |

安全要求：
- **以调用者身份执行**（OAuth2 令牌透传，不做"服务账号万能读"——否则 MCP 就是最大的越权后门）；
- **⚠️ 按 2026-07-28 正式规范实现（不是 RC），其核心变化是无状态化（移除 session）**：会话级上下文不再由协议隐式承载，**身份、权限与审计必须逐请求显式传递**——这一点必须写进接口契约，否则会在升级规范时推翻授权设计（`research/04` 补充 21–28 已核实 MCP 2026-07-28 为正式规范，且**已于 2025-12-09 随 AAIF 捐赠给 Linux Foundation**，"Anthropic 的 MCP"表述已过时）；
- **最容易踩的坑**：OAuth 请求若**省略 RFC 8707 的 `resource` 参数，会导致 audience 错误并让每次调用返回 401**；
- 每个工具的输出都做权限裁剪与敏感过滤，返回内容带 `masked: true` 标注；
- 写类操作永远走 Suggestion/审批，Agent 无直写权限；
- 全量调用审计（谁、何时、通过哪个 Agent、查了什么）。

## 7. AI 反模式（明确禁止）

1. **AI 直接写正式元数据**（无审批、无 provenance）→ 目录失去可信度，比没人填更糟。
2. **把全量元数据/采样数据发给外部 LLM** → 合规灾难。
3. **用 LLM 做血缘的主来源** → 错误的血缘会污染影响分析、合规传播与 AI 上下文本身（错误自我放大）。
4. **无引用的问答** → 用户无法验证，最终不信任整个平台。
5. **没有评估集就上 prompt 变更** → 静默质量退化。
6. **让 AI 生成"看起来专业"的空话描述** → 催生元数据垃圾，拉低信噪比（比没有描述更差）。
7. **对高风险建议（分级降级、策略豁免）开自动应用** → 直接造成安全事件。
8. **服务账号绕过用户权限** → 越权数据泄露的第一大来源。
