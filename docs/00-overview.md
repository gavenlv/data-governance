# 通用数据治理平台 · 总体方案（Draft v0.1）

> 本文档是整套方案的入口。范围：**调研 → 分析 → 规划 → 设计 → 方案草案**，不含实现。
> 全部文档见文末「文档索引」。

---

## 0. 一页纸摘要（TL;DR）

**做什么**：自建一个**通用的数据治理平台**——统一元数据底座 + 数据目录 + 血缘 + 质量 + 契约 + 分类分级 + 访问策略 + 治理运营 + AI 原生能力。

**为什么自研**：现成开源（OpenMetadata / DataHub）已能把"目录 + 血缘"做得不错，但**普遍停在"元数据层"**：不下发数据面策略、不解决企业真正的权限与合规闭环、AI 能力粗放且不可审计。商业产品（Collibra / Informatica / Alation / Atlan）在这些方面成熟，但贵、闭源、模型私有、迁移锁定。自研的正当理由只有一个：**要做"元数据 → 数据面策略执行"的闭环与深度定制**。若不要这个，应该二开而不是自研。

**怎么做**（六条立场）：
1. 元数据是产品而非文档（要被 CI/引擎/BI/Agent 消费）；
2. 单一真相源 + 可重建派生视图（不再犯"多处平级双写"的行业通病）；
3. 治理即代码（契约/策略/规则/术语 Git 化 + CI 门禁）；
4. 联邦治理（Domain / Data Product 一等公民）；
5. AI 产出必须可审计（建议 + 证据 + 人工确认，绝不直写）；
6. 开放标准优先（OpenLineage / ODCS / Iceberg REST / MCP）。

**关键取舍**：先做"发现与理解"（最快见效），再做"信任"（质量/契约），最后做"管控"（策略执行与联邦）。
**不做什么**：不做 ETL 调度、BI、查询引擎、MDM、通用 BPMN。

**代价（必须被决策层看到）**：前 6 个月没有"成品"，需要 3–4 名核心工程稳定投入 18 个月；连接器广度需要 2–3 年追赶开源社区。

## 1. 我们要解决的真实问题

| 现状痛点 | 表现 | 本方案的对应能力 |
|---|---|---|
| **找不到数据** | 靠 IM 问人、"这张表谁建的" | 搜索 + 术语表 + 语义检索 + 行为元数据推荐 |
| **看不懂数据** | 有表无描述、口径靠口口相传 | 描述/文档 + 血缘 + 指标口径 + 中文语义检索 |
| **不敢用数据** | 不知道数据质量、不知道会不会变 | 质量规则 + 剖析 + SLO + 契约 + 变更影响分析 |
| **管不住权限** | 权限靠工单与人工 GRANT，批了没人回收 | 访问申请审批 + 策略编译下发 + 到期回收 + 审计 |
| **合规无证据** | 审计来了临时翻系统 | 分类分级（列级传播）+ 访问审计 + 合规报告一键导出 |
| **治理无抓手** | "请各位完善元数据"喊了半年没人做 | 健康分 + 待办中心 + 域记分卡 + 采纳度 KPI |
| **AI 无处下手** | 想做 ChatBI / Agent，但模型不知道数据是什么 | 可被 Agent 消费的元数据（MCP）+ 语义层接入 |

## 2. 调研结论（三句话）

1. **OpenMetadata**（开源，一体化模型最强）：单一 JSON-Schema 驱动的实体模型、最广的连接器覆盖、开箱即用的一体化体验（目录 + 血缘 + 质量 + 契约 + 术语）——**最值得抄的是"开箱可用"与模型统一性**；短板在策略执行、AI 深度与大规模性能。
2. **DataHub**（开源，架构最优雅）：Entity/Aspect/URN 模型 + MCE/MAE/MCL 事件驱动 + "一切皆实体"——**最值得抄的是事件驱动与可扩展性**；坑在 Kafka/图库重依赖与三处平级双写导致的一致性运维负担。
3. **商业平台**（Collibra / Informatica / Alation / Atlan / Purview / DataZone 等）：**最值得抄的是治理运营与策略执行**——工作流与 Operating Model（Collibra）、CLAIRE 式的元数据驱动 AI 推荐（Informatica）、查询日志驱动的行为元数据与"人气"排序（Alation/Amundsen）、现代协作 UX 与资产 360（Atlan）、扫描器 + 分类器 + 合规标签体系（Purview）。它们普遍做得好的，恰是开源普遍做得弱的：**审批流、策略下发、合规证据、治理运营度量、开箱 AI**。

> 完整调研见 `docs/research/01`–`05`，综合对比与"取各所长"见 `06-competitive-synthesis.md`。

## 3. 方案定位与差异化

**一句话定位**：OpenMetadata 的"开箱可用" + DataHub 的"事件驱动与可扩展" + 商业产品的"策略执行与治理运营"，减去三者各自的运维地狱。

七项差异化设计（每项都能对应到"别人做得不好的地方"）：

| # | 差异化 | 解决谁的痛点 |
|---|---|---|
| 1 | **派生视图可重放重建**（PG 真相源 + outbox 事件流；图/搜索/统计全部可丢弃重建） | DataHub 的索引漂移与升级重建痛点 |
| 2 | **血缘四路汇聚 + 置信度显性化**（解析/运行时/日志/人工，带来源、置信度、时效、冲突标记、待确认队列） | 全行业"血缘不准且用户无法判断"的抱怨 |
| 3 | **策略编译与下发到数据面**（行过滤/列掩码下发 Trino/Spark/数仓/BI） | 开源平台不做、企业最痛 |
| 4 | **契约与治理门禁进 CI**（ODCS + 兼容性 diff + 血缘影响 PR 评论） | 治理与研发流程脱节的通病 |
| 5 | **AI 产出走 Suggestion + provenance + 人工确认**（可审计、可回滚、可评估） | AI 元数据的信任与合规风险（2026 年 Agent 直接消费元数据后风险更高） |
| 6 | **治理运营闭环**（健康分 → 待办中心 → 域记分卡 → 采纳度 KPI） | "上线没人用"这一治理平台头号死因 |
| 7 | **Pull + Edge Agent 双模采集**（支持私有子网、数据不出域） | 开源项目普遍只支持服务端拉取 |

## 4. 架构一览

```
L5 体验与开放：Web UI │ CLI │ SDK │ GraphQL/REST │ Webhook │ CI 插件 │ 嵌入式 │ MCP
L4 治理能力：  术语 │ 质量与可观测 │ 契约 │ 分类分级 │ 策略与访问 │ 记分卡 │ AI 建议
L3 元数据核心：Model Registry │ 实体/方面/关系 │ 版本与审计 │ 血缘 │ 图查询（真相源）
L2 派生视图：  搜索索引 │ 向量索引 │ 血缘闭包 │ 统计宽表 │ Feed（全部可重建）
L1 接入：      Connector 框架 │ Edge Agent（推） │ OpenLineage 端点 │ 外部 Catalog 联邦
纵轴：多租户/SSO/密钥/调度/工作流/通知  ·  可观测/备份/升级/自身合规
```

技术选型主轴：**Java/Kotlin 控制面 + PostgreSQL 真相源 + 事件流 + OpenSearch 派生索引 + Python 侧车（sqlglot 血缘解析 / AI）+ Go 采集 Agent + 授权（RBAC+ABAC+层级继承，细粒度 ReBAC 预留 OpenFGA）+ K8s/Compose 双形态**。
（详见 `07-platform-architecture.md`、`10-tech-stack.md`）

## 7. 最贵的五个决定（也是最容易做错的）

| # | 决定 | 我们的选择 | 为什么 |
|---|---|---|---|
| 1 | 元数据主存 | PostgreSQL 单库（JSONB + 边表 + 递归查询） | 强一致 + 无分布式复杂度；图库按需作派生视图 |
| 2 | 变更传播 | 事务内 outbox → 事件流 → 派生视图 | 杜绝多处平级双写导致的不一致 |
| 3 | 血缘可信 | 边带 source/confidence/freshness/conflict | 宁可承认不确定，也不展示"看起来对但错"的血缘 |
| 4 | AI 写入 | 只走 Suggestion + provenance + 人工确认 | 无审计的 AI 元数据比没有元数据更危险 |
| 5 | 部署形态 | 模块化单体 + 按需拆 Worker；Pull 与 Agent 双模 | 反对过早微服务化；企业网络现实必须支持推模式 |

## 8. 主要风险（含退出条件）

| 风险 | 触发信号 | 应对 / 退出 |
|---|---|---|
| 范围失控 | 每季度新增 3 个以上能力域 | 冻结范围，回到 MVP 故事 |
| 血缘可信度不足 | 抽查正确率 < 70% | 收敛到运行时上报 + 关键链路，放弃全量解析 |
| 无人使用 | 上线 3 个月周活 < 20% | 停新功能，转"现场嵌入 + 灯塔场景"；否则转二开 |
| 连接器维护失控 | 源系统升级波及 > 20% 连接器 | 限制支持清单，抽象版本兼容层 |
| 团队不持续 | 核心人员流失且无 owner | **诚实转为二开 OpenMetadata/DataHub**（见 `12` 退出条件） |
| 与既有平台重复 | 公司已满意地跑着 DataHub/OM | 重新评估 build vs buy |

## 10. 下一步：需要拍板的 7 件事

1. **是否走"自研内核 + 复用生态件"的混合路线**（否则整体转二开，本方案作废重做）；
2. 多租户语义：逻辑隔离 or 强隔离；
3. 是否要求信创/国产化适配（影响中间件选型）；
4. AI 是否允许外部 LLM 调用（影响私有模型与向量库成本）；
5. 首要痛点排序（决定 MVP 侧重；本方案默认"目录 + 血缘"）；
6. 是否有既存治理工具需共存/迁移（可能占 MVP 30% 工作量）；
7. **平台长期 owner 与团队编制**（3–4 人 × 18 个月）——这一条不确认，其余都无意义。

> 评审建议：先只审 `00`（本文）+ `12`（决策框架）两页，确认方向；通过后再审 `07`/`08`（架构与模型）的细节。
