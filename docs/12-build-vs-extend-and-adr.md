# 12 · 自研 vs 二开 vs 采购，与关键架构决策（ADR）

> 状态：Draft v0.1
> 这一份文档的目的是**让决策层能在 30 分钟内做出"该不该自研"的判断**，以及让工程团队有明确的决策记录可追溯。

---

## 第一部分：Build vs Extend vs Buy

### 1. 三条路线的真实面貌

| 维度 | A. 采购商业产品 | B. 直接用/二开开源（OpenMetadata、DataHub） | C. 自研（本方案） |
|---|---|---|---|
| 到首次价值时间 | 1–3 个月（以采购与集成为主） | 2–6 周（部署 + 配采集） | 5–6 个月到灯塔域可用 |
| 3 年总成本 | 高（许可按资产/席位，常 6–7 位数/年，且随规模涨） | 低到中（人力 + 基础设施；二开人力不确定） | 高（6–10 人年 + 长期维护） |
| 功能广度（连接器、开箱能力） | 最全（且经过大量客户打磨） | 中高（OM 连接器最多） | 从 0 开始，需要 2–3 年追赶广度 |
| 深度定制能力 | 极低（受产品路线与 API 边界限制） | 中（受架构与升级成本限制） | 完全可控 |
| **数据面策略执行**（行/列级策略下发到引擎） | 部分厂商有（并常需配套产品） | 基本没有 | **可做（核心差异化）** |
| 与内部系统深度集成 | 中（靠 API） | 中 | 完全可控 |
| 升级与维护负担 | 厂商负责 | 自担（fork 后升级是地狱） | 自担（但可控） |
| 锁定风险 | 高（数据模型私有、迁移成本高） | 低（Apache-2.0） | 无（自有） |
| 组织学习价值 | 无 | 中 | 高 |

### 1.1 采购的两项隐性优势（自研无法享有，必须诚实计入）

来自 `research/03` §6 的反向补充：

1. **云市场承诺额度可核销**：主流商业产品均可通过云市场（Snowflake Marketplace / Databricks / Azure / AWS）采购，**能把支出从"新增预算"变成"已承诺预算的核销"**。自研不能。这一条在预算紧的年份往往比功能对比更能决定结果。
2. **供应商承担升级与 SLA**：订阅费换来的是"升级、迁移、可用性由别人负责"。自研时这些必须以人力折算（见 `11` §4 的隐性成本）。

> 这两条不构成"不要自研"的理由，但**必须在立项材料里被正面回答**：我们准备好用自己的预算和人力承担这两项了吗？

### 2. 决策框架（用问题定位，而不是用偏好争论）

```
Q1 你的核心痛点是"没有目录"，还是"目录有了但管不住数据权限/质量/合规"？
     ├─ 前者 → 采购或直接用开源，6 个月内解决；不要自研
     └─ 后者 → 自研有正当理由（尤其数据面策略执行），继续 Q2

Q2 现成开源能否通过"配置 + 少量插件"解决 80% 需求？
     ├─ 能 → 二开（Extend）：以 OM/DataHub 为底座，只开发缺失的 20%
     └─ 不能 → 继续 Q3

Q3 你的差异化需求是否集中在"平台内核"（元数据模型、血缘、策略、AI）？
     ├─ 是 → 自研内核 + 复用生态组件（本方案）
     └─ 否（只是缺几个连接器/报表）→ 回到二开

Q4 你是否有 5 人以上、能稳定投入 18 个月的平台团队，且有长期 owner？
     ├─ 是 → 自研可行
     └─ 否 → 强烈建议二开或采购（自研平台最怕的是"半年后没人维护"）
```

### 3. 推荐路线：**自研内核 + 复用生态件 + 二开补丁**（"第三条路"）

这是本方案的实际主张。**不要把它理解成"全部自己写"**：

| 层 | 决策 | 说明 |
|---|---|---|
| 元数据模型与核心服务 | **自研** | 这是平台的灵魂与差异化，别人写的不能改就是受制于人 |
| 事件流与派生视图机制 | **自研**（思想借鉴 DataHub） | 用 PG outbox / Kafka 实现，但纠正其三处平级双写的缺陷 |
| 血缘 SQL 解析 | **直接复用** sqlglot | 不重复造解析器；自己写方言语料回归集 |
| 血缘协议接入 | **直接复用** OpenLineage | 作为标准入口，不自定义作业上报协议 |
| 契约格式 | **直接复用** ODCS | 不发明契约标准；自己写 diff 与兼容性引擎 |
| 表格式/目录接入 | **直接复用** Iceberg REST / HMS / Glue API | 联邦而非同步 |
| 授权引擎 | **分阶段**：v1 平台自持层级继承 + 属性规则；v3 按需引入 OpenFGA | 不第一天就上 Zanzibar（复杂度失控） |
| 搜索与向量 | **直接复用** OpenSearch | 不自研检索引擎 |
| 连接器 | **移植/参考** OM 与 DataHub 的 Apache-2.0 实现 + 自研框架适配 | 这是最大的"省力点"，但必须做许可证合规与来源标注 |
| 质量规则生态 | **兼容** dbt tests / Great Expectations 语义 | 不要求用户迁移已有测试 |
| 语义层 | **集成** dbt Semantic Layer / Cube | 不自建指标计算引擎 |
| 工作流 | **复用** Temporal（复杂场景）/ 自研轻量状态机 | 不自研 BPMN |
| UI 组件与图谱渲染 | **复用** Ant Design / Cytoscape / G6 | UI 自研的是"信息架构与交互"，不是组件库 |

一句话总结：**自研"如何组织与消费元数据"，复用"如何获取与计算元数据"。**

### 4. 什么情况下应该放弃自研（诚实的退出条件）

出现以下任一情况，应转向二开或采购，而不是硬撑：
1. 团队无法保证 18 个月内 ≥ 4 名全职工程（自研平台的维护是长期税）；
2. 核心诉求只是"能搜到表、能看到血缘"——开源已经够用；
3. 组织没有数据治理的**权责体系**（无 Owner、无委员会、无考核）——自研一个没人用的平台是纯浪费；
4. 公司战略要求"快速满足一次合规审计"——采购比自研快 5 倍且风险更低；
5. 已有人均满意度尚可的 DataHub/OM 部署且团队规模 < 500 人。
6. **"Elementary + OpenMetadata 组合"已经能满足目录 + 质量需求**（见下）。

### 4.1 必须承认的直接竞品：Elementary（免费 + 可自托管 + 生产级）

`research/03` §7.8 的判断值得原文照录：

> **Elementary 是唯一免费、可自托管的生产级选项，且其"计算推进数仓、平台侧只做 UI 与协作"的架构就是自建方案最好的参考形态。若自建平台在「目录 + 质量」范围内无法显著超过"Elementary + OpenMetadata 组合"，则立项理由只剩 D7 策略执行与 D8 治理运营。**

因此本方案的自研理由被**收敛为两条**（其余一律可以用现成组件满足）：
- **D7 访问治理与策略执行**（策略编译下发到数据面）——开源不做，商业侧仅 AWS 等少数做到闭环；
- **D8 治理运营闭环**（健康分 / 待办 / 记分卡 / 采纳度）——开源止于覆盖率统计，商业侧成熟但封闭。

如果这两条在你的场景里也不重要，**正确结论是二开而不是自研**。

## 第二部分：关键架构决策记录（ADR）

> 格式：决策 / 背景 / 考虑的选项 / 结论 / 后果与代价 / 复审触发条件

### ADR-001 元数据存储：PostgreSQL 单库作为真相源
- **背景**：需要强一致、事务、关系查询、JSON 灵活性、时间旅行，且团队规模有限。
- **选项**：(a) PostgreSQL + JSONB；(b) MySQL；(c) MongoDB；(d) Elasticsearch 当主存；(e) 图数据库当主存。
- **结论**：**(a)**。JSONB 天然匹配 Aspect；递归 CTE 支持血缘多跳；运维成熟、人才充足、备份与只读副本方案标准。
- **代价**：超大规模（亿级边 + 深跳）需要物化或引入派生图库；JSONB 复杂查询需谨慎索引。
- **复审触发**：单表 > 5 亿行或血缘 5 跳查询 P95 > 3s。

### ADR-002 变更传播：事件流 + 可重建派生视图（不做多存储平级双写）
- **背景**：搜索索引、图、统计视图都需要元数据；DataHub 的做法是各自消费 MCL，导致漂移与 `restore-indices` 兜底。
- **选项**：(a) 应用层同步双写；(b) 定时全量重建索引；(c) **PG 真相源 + 事务内 outbox → 事件流 → 消费者构建派生视图**。
- **结论**：**(c)**。写入与事件在同一事务（outbox）保证不丢；消费者可重放；新增视图只是新增消费者。
- **代价**：引入最终一致（需 watermark 与"索引同步中"提示）；需要实现幂等消费者与重放工具。
- **复审触发**：事件积压持续 > 10 分钟或重放时间 > 4 小时。

### ADR-003 血缘存储：v1 不引入图数据库
- **背景**：血缘是图问题，但图库（Neo4j/JanusGraph/HBase）带来独立运维、备份、技能与一致性负担。
- **选项**：(a) 图库作主存；(b) PG 边表 + 递归查询；(c) 纯内存图缓存。
- **结论**：**(b)**，配合 1–3 跳物化闭包；图库仅在实测不达标时作为**派生只读视图**引入（ADR-003-R1）。
- **代价**：深跳查询与复杂图算法（社区发现、路径排序）能力弱于专用图库。
- **复审触发**：亿级边场景或需要图算法（相似度传播、社区聚类）。

### ADR-004 血缘可信度显性化：边带 source/confidence/freshness
- **背景**：血缘不准确是行业普遍抱怨；根因是把不同可靠性的来源混为一谈，用户无法判断。
- **选项**：(a) 只存边；(b) 存边 + 来源；(c) **存边 + 来源 + 置信度 + 时间衰减 + 冲突标记 + 待确认队列**。
- **结论**：**(c)**。宁可展示"这条血缘不确定"，也不要展示"看起来确定但错误"的血缘。
- **代价**：模型与 UI 复杂度上升；需要人工确认工作流。
- **复审触发**：无（长期原则）。

### ADR-005 采集默认"绝不覆盖人工内容"，并提供采集级批量回滚
- **背景**：客户最常见投诉是"我写的描述被采集覆盖了"与"错误采集污染了目录无法回退"。
- **结论**：字段级 source 优先级（MANUAL > IMPORTED > AUTO）；采集变更集整体可回滚；异常变更比例阈值自动挂起。
- **代价**：需要字段级来源追踪与变更集存储；UI 需呈现来源。
- **复审触发**：无。

### ADR-006 控制面 Java/Kotlin，解析与 AI 用 Python 侧车，采集 Agent 用 Go
- **背景**：三种能力的最优生态不在一门语言里。
- **选项**：(a) 全 Java（含 Calcite 解析）；(b) 全 Python；(c) **多语言但边界清晰**。
- **结论**：**(c)**。sqlglot 的方言覆盖与列级血缘能力无可替代；LLM/统计生态在 Python；数据侧 Agent 需要零依赖二进制。
- **代价**：三套 CI/发布/依赖治理；跨语言调试成本；团队技能要求高。
- **复审触发**：团队无法维持多栈，或 Calcite 方言覆盖追平（则收敛为 Java 单栈）。

### ADR-007 AI 产出走 Suggestion 实体，禁止直写
- **结论**：所有 AI 生成的元数据先落 Suggestion（含 provenance/confidence/证据引用），人工接受后写入；高风险类别禁止自动应用；每批可回滚。
- **代价**：增加"人工审阅"环节（这恰恰是价值：AI 省 80% 起草时间，人保 20% 判断）。
- **复审触发**：建议采纳率与质量长期稳定在极高水位（> 90% 且零事故）后，可对低风险类别放宽。

### ADR-008 策略执行采用"编译 + 下发"，而非只在平台内鉴权
- **背景**：企业真正的风险在数据本身被谁读取，而不是谁看到了资产卡片。
- **结论**：策略在平台建模 → 编译为目标引擎产物（Trino/Spark 行过滤与掩码、数仓原生策略、BI 可见性）→ 灰度下发 + 回滚；编译器用快照测试锁死行为。
- **代价**：需要与查询引擎/BI 团队协作；错误策略影响面大（必须有灰度与回滚）。
- **复审触发**：目标引擎不提供策略下发能力时降级为"策略导出 + 人工实施 + 合规校验"。

### ADR-009 授权分阶段：v1 自建 RBAC + ABAC + 层级继承，细粒度关系授权再引入 OpenFGA
- **背景**：需要同时管"平台功能权限""资产可见性""数据行/列访问"，且权限错误后果严重（泄露或大面积不可用）。调研（`research/04` §3.3）明确指出：**一步到位上 Zanzibar 式 ReBAC 容易失控**。
- **选项**：(a) 引入 OpenFGA/SpiceDB 作为授权引擎；(b) 全自研 RBAC+ABAC；(c) **分阶段：v1 平台自持"层级继承 + 属性规则 + 授权记录"，v3 按需引入 OpenFGA**。
- **结论**：**(c)**。元数据天然是层级结构（Container→Dataset→Column），继承式判定即可覆盖绝大多数场景；属性规则处理分级/域/标签维度；授权记录（谁、什么粒度、多久）作为独立实体支撑审计与回收。仅当出现跨组织、多维关系的授权诉求时才引入 OpenFGA。
- **代价**：自建判定逻辑需要严格的测试覆盖（越权用例必须进 CI）；未来迁移到 OpenFGA 需要模型映射与双跑验证。
- **复审触发**：出现"无法用层级 + 属性表达"的授权诉求（跨域/跨组织关系推导），或授权判定成为性能瓶颈。
- **⚠️ 调研分歧记录（必须知道）**：`research/04` §3.3 主张"先 RBAC → 加资源层级继承 → 最后才评估 OpenFGA"，`research/05` §10 则主张"授权直接用 SpiceDB/OpenFGA + OPA/Cedar（ABAC 交给通用策略引擎）"。
  两者的分歧点是**起点不同**：05 假设"授权引擎是成熟积木，直接用省事"，04 强调"权限模型未定型时引入 ReBAC 会同时设计 tuple 模型与业务语义，成本高且易失控"。
  **本方案采纳 04 的路线，理由**：① v1 的授权诉求以"容器→表→列的继承 + 分级/域/标签属性"为主，自持实现可覆盖；② 权限错误的后果（泄露/大面积不可用）要求模型先稳定；③ 若团队**已有** OpenFGA/SpiceDB 运维经验，则应改采 05 的建议（此时"直接用"确实更省）。
  无论走哪条，**"工具级授权（MCP/Agent 调用）从第一天就要设计进授权层"**（`research/04` §6）：事后补授权几乎必然重构。


### ADR-010 模块化单体优先，按需拆分服务
- **结论**：v1 单体（清晰模块边界 + 内部 API），仅对血缘解析、AI、质量执行等异步重负载按需拆分独立 Worker。
- **代价**：单体部署规模上限；需要纪律维护模块边界（用架构测试如 ArchUnit 强制）。
- **复审触发**：单模块资源争抢影响前台 SLO，或团队 > 15 人需要独立发布节奏。

### ADR-011 对外标准优先（OpenLineage / ODCS / Iceberg REST / MCP）
- **结论**：外部接口对齐开放标准；平台内部模型可扩展但不作为对外契约。
- **代价**：标准演进跟随成本；标准覆盖不到的能力需额外扩展字段（放在 `extensions` 命名空间，避免污染标准语义）。
- **复审触发**：所依赖标准出现破坏性变更或停滞。

### ADR-012 采集部署：v1 同时支持 Pull 与 Edge Agent Push
- **背景**：企业普遍存在私有子网、多网络域、数据不出域诉求；只支持 Pull 会导致大量环境无法接入。
- **代价**：两套部署与运维路径；Agent 升级与安全（Agent 权限过大风险）。
- **复审触发**：无（这是企业落地的硬约束）。

## 第三部分：仍需业务方拍板的开放问题

| # | 问题 | 影响 | 建议默认 |
|---|---|---|---|
| Q1 | 自研的边界是否接受"混合路线"（内核自研 + 连接器复用开源）？ | 决定 6–12 个月的人力投入 | 接受；不接受则整体转二开 |
| Q2 | 多租户语义：逻辑隔离还是强隔离？ | 权限模型、部署拓扑、成本 | 逻辑隔离默认 + 可选独立实例 |
| Q3 | 是否要求信创/国产化适配（数据库、OS、CPU、中间件）？ | 中间件选型（OpenSearch/Kafka 能否用国产替代） | 预留适配层，v1 不自缚 |
| Q4 | AI 是否允许调用外部 LLM？数据出境限制？ | AI 架构（私有模型 + 本地向量库成本） | 默认禁用外部调用高敏上下文；提供私有模型方案 |
| Q5 | 首要痛点排序（发现 / 血缘 / 质量 / 合规 / 权限）？ | MVP 侧重 | 目录 + 血缘 |
| Q6 | 是否有既存治理平台/工具需要共存或迁移？ | 集成与迁移工作量（可能占 MVP 30%） | 先做只读集成，不做替换承诺 |
| Q7 | 合规框架范围（GDPR / 个保法 / 行业监管 / 等保）？ | 分级体系、审计要求、保留策略 | 分级可配置 + 审计完整，先满足通用要求 |
