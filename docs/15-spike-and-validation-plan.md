# 15 · 立项前技术验证计划（Spike Plan）

> 状态：Draft v0.1
> 目的：在设计冻结与投入 18 个月人力之前，用 **4–6 周、1–2 人** 验证 6 个"如果错了整个方案就要改"的技术假设。**先证伪，再开工。**

---

## 1. 为什么需要这一步

本方案有若干"看起来合理但没有实证"的关键假设。它们在纸面上无法判断，一旦进入正式开发才发现不成立，代价是数月返工。Spike 的目标不是做出功能，而是**用最小成本把假设变成数据**。

原则：
- 每个 Spike 有**可量化通过标准**与**明确失败后的对策**（预先约定，避免事后找理由）；
- 不做 UI，不做生产级代码，允许硬编码与本地运行；
- 时间箱（time-box）严格，超时即停止并记录结论；
- 复用真实数据（脱敏后的生产元数据/SQL 语料），不用玩具数据自欺。

---

## 2. Spike 清单

### S1 · 列级血缘解析准确率（最高风险，最高价值）
**假设**：以 sqlglot 为核心的列级血缘，在客户真实 SQL 语料上能达到可用精度。

| 项 | 内容 |
|---|---|
| 方法 | 抽取 500–1000 条真实 SQL（覆盖 Hive/Spark/Trino/MySQL/Doris 方言、CTE、窗口函数、`SELECT *`、动态 SQL、存储过程），跑解析，输出列级映射；随机抽 100 条人工比对。**同时对比 sqlglot 与 Apache Calcite 在 100 条核心数仓 SQL 上的结果差异**（`research/04` §2.1 的倾向是"sqlglot 主 + Calcite 对核心层二次校验"——本 Spike 要验证：二次校验能否真的揪出 `SELECT *` 展开、JOIN 列歧义、类型隐式转换这类错配，以及双解析器的维护代价是否可接受） |
| 通过标准 | 解析成功率 ≥ 90%；成功解析的样本中列级映射正确率 ≥ 95%；**失败必须显式降级为表级并标记**（不允许静默返回空）；双解析器**不一致率**（sqlglot vs Calcite 在核心层）能被度量且不一致项可进人工/运行时复核队列 |
| 失败对策 | ① 收敛范围：只承诺主要方言；② 补齐运行时上报（OpenLineage）为主渠道；③ 引入商业解析库评估（如第三方 SQL 血缘服务） |
| 交付 | 解析报告（按方言/语句特征分组的成功率）、失败原因分类、语料回归集雏形（长期资产）。**回归机制建议用 sqlglot 自带的 Executor 做小样本回放**——它能在不连真实数据的情况下验证"血缘规则本身"的正确性（`research/04` 附录·补充 17），显著降低后续规则回归成本；另需在 Spike 中确定 `error_level`/`max_errors` 的取值（批量解析时一条坏 SQL 会中断整批） |

### S2 · PostgreSQL 血缘查询性能（架构基石）
**假设**：PG 边表 + 递归 CTE + 物化闭包，能支撑目标规模的血缘查询 SLO。

| 项 | 内容 |
|---|---|
| 方法 | 造数：**v1 适用范围 500 万实体 / 5000 万边**（含 DAG 与"宽扇出"两类拓扑，宽扇出是递归查询杀手）+ 2 倍压力档；测 1/3/5 跳上下游查询、影响分析、列级路径追踪；**必须实测 `lineage_closure_mv`（depth≤3）在真实拓扑下的行数与刷新耗时**——这是 `19` 评审 B1 指定的硬指标，超阈值即改走"仅物化跨域与关键路径闭包" |
| 通过标准 | 3 跳 P95 < 1s；5 跳 P95 < 3s；物化闭包刷新不影响在线查询 |
| 失败对策 | 启用 ADR-003-R1：引入派生图库（NebulaGraph/HugeGraph）；或按域/平台分区 + 预计算关键路径 |
| 交付 | 基准脚本 + 数据生成器 + 实测报告（含 EXPLAIN 关键结论） |

### S3 · 采集"绝不覆盖人工内容"与批量回滚（信任基石）
**假设**：字段级来源优先级 + 采集变更集回滚，可工程化实现且不显著影响采集吞吐。

| 项 | 内容 |
|---|---|
| 方法 | 对 3 类源系统做两次采集，期间在平台侧人工编辑描述/标签/Owner，验证：人工内容是否被覆盖、删除是否可回滚、并发写是否冲突 |
| 通过标准 | 零覆盖事故；单次采集变更集可在 60s 内完整回滚；采集吞吐 ≥ 2k 实体/秒 |
| 失败对策 | 无法回滚则改为"变更集快照 + 差异补偿"；吞吐不足则放宽为批量 + 异步 |
| 交付 | 回滚正确性测试报告 + 语义定义文档（什么算"人工内容"） |

### S4 · 策略编译与下发（差异化核心，最不确定）
**假设**：平台建模的策略能可靠编译为 Trino/Spark 可执行的行过滤/列掩码，并安全下发。

| 项 | 内容 |
|---|---|
| 方法 | 定义一个真实场景（"风控组只能看本区域客户，手机号掩码"），编译为 Trino 行过滤与列掩码表达式、Spark 等价物；在测试集群灰度下发；做快照测试与错误注入 |
| 通过标准 | 生成的策略在引擎上语义正确（用查询验证：越权数据不可见）；错误策略可回滚；快照测试能捕获语义变更 |
| 失败对策 | 降级为"策略导出 + 人工实施 + 定期合规校验"；或只做列掩码（不做行级） |
| 交付 | 编译器原型 + 语义测试用例 + 与引擎的集成方式（推送 vs 拉取）结论 |

### S5 · Edge Agent 推模式采集（企业落地的硬约束）
**假设**：Agent 能在无入站连通性的私有子网内完成采集并安全上报。

| 项 | 内容 |
|---|---|
| 方法 | 在隔离网络模拟环境部署 Agent，采集数据库元数据，经出站 TLS 上报；测试断网续传、凭证轮换、Agent 升级、权限最小化 |
| 通过标准 | 零入站端口即可工作；断网 30 分钟不丢数据；凭证不落盘明文；单 Agent 覆盖 5 万实体 |
| 失败对策 | 改为"Agent + 本地中转服务"两级；或只支持公网可达环境的 Pull 模式（明确写进产品范围） |
| 交付 | Agent 原型 + 安全评审清单 |

### S6 · AI 建议质量与越权防护（决定 AI 是否上线）
**假设**：LLM 生成的描述/分类建议达到可被采纳的质量，且权限裁剪可防止信息泄露。

| 项 | 内容 |
|---|---|
| 方法 | 取 100 张真实表（含脱敏采样统计），生成描述与 PII 分类建议，人工评分（有用性/准确性/是否空话）；构造 20 条越权提问（询问无权资产的名称/内容）测试拦截 |
| 通过标准 | 描述建议采纳率 ≥ 40%（编辑后接受也算）；分类漏判率 < 5%；越权提问泄露率 = 0 |
| 失败对策 | 收紧场景（只做"基于已有描述的改写与补全"）；或推迟 AI 到更后期；分类回归纯规则 |
| 交付 | 评估集（长期资产）+ 拦截测试报告 + 成本估算（每千次建议的 token 成本） |

## 3. 时间安排与产出

| 周 | 内容 |
|---|---|
| W1 | 环境准备、真实语料与脱敏元数据准备（**准备期常被低估，务必留足**） |
| W1–W3 | S1 / S2 并行（数据与算法两条线） |
| W2–W4 | S3 / S5 并行（工程正确性与部署形态） |
| W4–W5 | S4 策略编译（需与引擎团队协作） |
| W5–W6 | S6 AI 评估 + 汇总报告与设计修订 |

产出物：
1. `spike-report.md`：每个假设的实测结论、是否成立、对设计的修订建议；
2. 可再生资产：SQL 语料回归集、血缘基准数据生成器、AI 评估集、策略语义测试用例；
3. **修订后的设计文档**（本套文档的 v0.2），以及"Go / 有条件 Go / No-Go"结论。

---

## 4. Go / No-Go 判定规则（提前约定）

| 结论 | 条件 |
|---|---|
| **Go** | S1、S2、S3 全部通过（其余可有条件通过） |
| **有条件 Go** | S1 或 S2 未达标但存在明确可行的对策（如收敛范围、引入派生图库） |
| **No-Go（转二开）** | S1 与 S2 同时未达标且无低成本对策；或 S3（不覆盖人工内容）无法实现；或始终找不到 3 人以上稳定团队 |

---

## 5. 与正式开发的衔接

Spike 的副产品应直接进生产代码库（而不是丢在个人分支）：
- SQL 语料回归集 → 血缘解析的 CI 黄金测试；
- 基准数据生成器与脚本 → 性能基准套件；
- AI 评估集 → AI 能力的 CI 门禁；
- 策略语义测试用例 → 策略编译器的快照测试；
- 采集回滚测试 → 集成测试用例。

**这样 Spike 的投入不会浪费：它同时产出了平台未来最需要的三类"防护网"（血缘语料、性能基准、AI 评估）。**
