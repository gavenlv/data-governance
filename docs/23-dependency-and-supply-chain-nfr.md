# 23 · 非功能需求：第三方依赖与供应链安全（NFR-SEC-01）

> 状态：**已生效**（含实测基线与自动化证据链）。
> 需求来源：公司合规与安全要求 —— "所选技术与第三方依赖不能有漏洞，或至少要把漏洞压到最低；
> 真有漏洞就要想办法替换，或者选择积极修复的 FOSS 依赖，保证系统的安全合规与持续性"。
> 相关：`docs/07 §8`（架构质量属性）、`docs/10 §1/§4`（技术选型与安全设计）、
> `docs/12` ADR-015（依赖治理策略）、`docs/21 §18`（落实记录）。

---

## 1. 需求陈述（正式 NFR）

**NFR-SEC-01 · 依赖与供应链安全**

> 平台所采用的技术组件与第三方依赖，**不得引入已知的 CRITICAL / HIGH 漏洞**；
> MEDIUM 及以下漏洞必须在规定时限内修复、替换或按例外流程登记。
> 选型优先采用**安全响应积极、维护活跃、许可清晰**的 FOSS 组件；
> 出现无法及时修复的漏洞时，必须给出**替换方案或隔离方案**，而不是长期挂账。
> 该要求适用于**运行时依赖**（进入交付产物的部分），并对构建期依赖同样做清点与扫描。

这条 NFR 有三个不可拆分的部分，缺任何一条都不成立：

| 部分 | 内容 | 为什么不能少 |
|---|---|---|
| **A. 门槛** | 无已知 CRITICAL/HIGH；MEDIUM 限时处理 | 只有"门槛"会退化成"上线前扫一次" |
| **B. 选型** | 优先积极修复、维护活跃的 FOSS | 只有"门槛"会让人一直选**没人修**的库，然后靠豁免过日子 |
| **C. 持续性** | 持续扫描 + 升级时限 + 替换/例外流程 + 证据留存 | 漏洞是**随时间**产生的：今天干净不代表下个月干净 |

## 2. 验收标准（可判定，不含"尽量""原则上"）

| 编号 | 验收标准 | 判定方式 |
|---|---|---|
| AC-1 | 运行时依赖中 **CRITICAL = 0、HIGH = 0** | `tools/dependency_audit.py` 退出码 0 |
| AC-2 | MEDIUM / LOW 漏洞**要么在时限内修掉，要么有登记在案的豁免** | 报告 + `security/dependency-waivers.yaml` |
| AC-3 | 扫描链路本身**经过反向验证**（能检出已知漏洞） | `tools/dependency_audit.py --self-test` 通过 |
| AC-4 | **扫描未完成不得等同于通过**（清点失败/网络不可达 → `UNVERIFIED` 且 CI 失败） | 工具退出码语义（0 / 1 / 2） |
| AC-5 | 不引入**未使用的依赖**；不引入**已停止安全维护**的版本线 | pom / package.json 评审 + 本文件 §6 清单 |
| AC-6 | 每个交付版本产出**依赖清单与扫描报告**（可归档给审计） | `security/reports/dependency-audit.json` |
| AC-7 | 修复时限：CRITICAL 7 天 / HIGH 30 天 / MEDIUM 90 天 / LOW 下个例行版本 | 扫描报告时间戳 + 版本发布记录 |

> AC-4 是这份 NFR 里最容易被忽略、也最危险的一条。绝大多数"我们扫过，没问题"的事故，
> 真相是**扫描器没跑成功**，而没人发现。

## 3. 修复时限与响应流程

| 严重度 | 修复时限 | 处置方式 |
|---|---|---|
| CRITICAL | **7 天** | 优先升级/替换；无法在时限内完成时，必须先**隔离**（关闭受影响特性/路径）再评估 |
| HIGH | **30 天** | 升级到修复版本；框架尚未发布修复版本时，自行固定已修复的补丁版本（见 §5 案例） |
| MEDIUM | **90 天** | 跟随例行升级；有豁免则登记 |
| LOW | 下个例行版本 | 记录即可 |
| UNKNOWN（严重度无法判定） | 按 MEDIUM 处理 | 必须人工复核一次：**不猜**严重度 |

流程：

```
扫描（CI/发布前） → 有阻断项？
   ├─ 否 → 归档报告，进入发布
   └─ 是 → 能升级？ ── 是 → 升级 + 重跑扫描
                     └─ 否 → 能替换？ ── 是 → 替换同类组件 + 重跑
                                        └─ 否 → 登记豁免（owner + 到期日 + 理由）
                                                 → 到期自动重新阻断
```

**"能替换"是这条 NFR 的实质要求**：不是"先豁免着"，而是"给出替代路径"。
本文件 §7 记录了本轮真实执行过的替代与升级。

## 4. FOSS 选型标准（B 部分的具体化）

选择或新增第三方依赖时，逐条核对；不满足的必须在评审里明确写下理由：

| # | 标准 | 判定线索 |
|---|---|---|
| 1 | **安全响应积极** | 有公开的安全政策/PSIRT 或 SECURITY.md；CVE 有明确修复版本；修复节奏以周/月计 |
| 2 | **维护活跃** | 近 12 个月有发布；issue/PR 有维护者回应；不是"归档/只读"状态 |
| 3 | **版本线受支持** | 所用主/次版本仍在官方支持窗口内（**不用 EOL 版本线**） |
| 4 | **许可清晰** | 许可证明确且与分发方式相容（本项目优先 Apache-2.0 / MIT / BSD / EPL） |
| 5 | **可替换性** | 存在活跃替代品或标准接口；不形成单点绑定（例如检索层可换 OpenSearch、侧车可换解析器） |
| 6 | **供应链痕迹** | 发布物可校验（签名/校验和）、有可读的变更记录；理想情况提供 SBOM |
| 7 | **依赖面小** | 不为一个小功能引入一棵大依赖树（"依赖也是攻击面"） |
| 8 | **企业内网可达** | 支持私有镜像/离线仓库（公司合规环境的硬约束） |

**同时明确"不选什么"**：已归档项目、长期无发布的库、仅有个人维护且无替代路径的关键组件、
许可不明或与分发冲突的组件、以及**已引入但没人用的依赖**（见 §5 第 3 条）。

## 5. 落地机制（C 部分：怎么保证一直有效）

| 机制 | 实现 | 说明 |
|---|---|---|
| **依赖清点** | `tools/dependency_audit.py` | Maven 走 `dependency:tree`（dg-api 即完整运行时集）、npm 走 `pnpm list --prod --depth=Infinity`、Python 走实际安装版本 |
| **漏洞扫描** | 同一工具，查 **OSV**（osv.dev） | OSV 聚合 GitHub Advisory / NVD / GHSA，无需 NVD API key，适合放进流水线 |
| **严重度判定** | 数据库自带分级优先，否则**自算 CVSS v3 基础分** | OSV 给的是**向量**不是分数，不算就只能靠猜 |
| **例外台账** | `security/dependency-waivers.yaml` | 精确到漏洞 ID + 包；必须有 reason / owner / expires；**到期即重新阻断** |
| **反向自检** | `--self-test` | 用已知含漏洞的版本验证扫描链路，防止"扫描器坏了"被读成"干净" |
| **证据留存** | `security/reports/dependency-audit.json` | 每次运行生成，含时间戳、清单数量、全部发现项 |
| **CI 门禁** | 退出码 0/1/2 | 0=干净；1=有阻断项；**2=未验证**（清点失败/扫描失败）——三种语义在流水线里必须区分 |

CI 步骤（示例，放进任意流水线即可）：

```powershell
python tools/dependency_audit.py --self-test      # 先证明扫描链路有效
python tools/dependency_audit.py                  # 再判定：0 通过 / 1 阻断 / 2 未验证
```

## 7. 本轮实测与修复记录（可复现）

### 7.1 基线：升级前的真实数字

用 `tools/dependency_audit.py` 对 **Spring Boot 3.1.0** 的产物实测：

```
依赖清点：Maven 98 · npm 79 · PyPI 8
扫描：95 条已知漏洞（CRITICAL 10 · HIGH 42 · MEDIUM 33 · LOW 10）
阻断项集中在框架托管的传递依赖上：
  tomcat-embed-core 10.1.8   25 条（含 7 项 CRITICAL）
  jackson-databind  2.15.0    5 项 HIGH
  spring-web/webmvc 6.0.9     6 项 HIGH
  spring-security-* 6.1.0     1 CRITICAL + 4 HIGH
  logback / snakeyaml / micrometer / spring-boot 3.1.0 各若干
```

**结论**：这些不是"某个库没跟上"，而是**整条版本线已停止安全维护**的必然结果
（3.1.0 发布于 2023-05，其 OSS 支持早已结束）。仅靠逐个打补丁无法收敛，必须抬升版本线。

### 7.2 案例一：框架托管版本落后于修复版本（Tomcat）

升级到 Spring Boot 3.5.16 后，仍有 3 项 CRITICAL：框架托管的 Tomcat 是 10.1.55，
而修复版本是 10.1.58。框架补丁有发布节奏，CRITICAL 不等人，因此**显式覆盖**：

```xml
<tomcat.version>10.1.60</tomcat.version>
```

**一个只有真跑才会发现的细节**：OSV 给出的修复版本是 `10.1.58`，
但 Maven Central 上**根本没有发布 10.1.58**（10.1.57 之后直接是 10.1.59）。
若无脑按 OSV 的 `fixedIn` 去固定版本，构建会直接失败。
因此工具只把 `fixedIn` 作为**人工判断的输入**，不做自动改版本 ——
"自动升级"在供应链里是危险的自动化。

同类覆盖：`jackson-bom 2.21.7`、`commons-lang3 3.18.0`、`log4j2 2.26.1`。
这些覆盖都写在 `backend/pom.xml` 的注释里（含漏洞编号），并在 §5 要求**每次升级框架后重新核对**。

### 7.3 案例二：前端依赖的替换式修复

`pnpm audit` 与 OSV 均报 `react-router` 6.x：
open redirect（`CVE-2025-68470` 绕过）与 SSR 场景的构造函数注入。
两者都是 MEDIUM，但**升级成本很低**（v7 的声明式 API 与本项目用法兼容），因此直接升级：

```
react-router-dom 6.30.6 → 7.18.4
```

升级后 `pnpm build` 与界面渲染检查（9/9 标签页）全部通过。

### 7.4 案例三：删除未使用的依赖

`backend/pom.xml` 里声明了 `jjwt-api / jjwt-impl / jjwt-jackson`，
但全仓库**没有任何代码引用它们**（当前是静态令牌认证；OIDC/JWKS 尚未实现）。
不用的库同样进产物、同样要跟着打补丁，是纯粹的负担 → **直接移除**。
将来真正实现 OIDC 时按 §4 的标准重新选型，而不是默认回到 jjwt。

### 7.5 修复后的实测结果

```
依赖清点：Maven 99 · npm 80 · PyPI 8      （187 个依赖）
扫描：0 条已知漏洞（阻断 0 / 豁免 0 / 中低风险 0）
自检：jackson-databind@2.21.4 检出 9 条、react-router@6.30.6 检出 2 条 → 扫描链路有效
```

**"0 条漏洞"之所以可信，是因为自检先证明了扫描器在工作。** 这正对应 AC-3 / AC-4。

### 7.6 升级后的回归验证（同一轮完成）

依赖升级不是"改个版本号就完事"，必须重跑证据链：

```
mvn -B -o test                  → 142 项 Java 单测全绿（Boot 3.1.0 → 3.5.16 零代码改动）
python tools/java_e2e_verify.py → 123/123 通过
python tools/ui_render_check.py → 9/9 标签页渲染通过（react-router 7）
python -m pytest -q             → Python 参考实现全绿（250 项）
cd web && pnpm build            → 通过
python tools/dependency_audit.py --self-test → 通过
python tools/dependency_audit.py             → 0 条漏洞（退出码 0）
```

> 升级回归过程中还修正了一处 **e2e 断言自身的缺陷**（建议生成幂等的判定条件写错，
> 把"候选池正常补位"误判为"幂等失效"）—— 记录在 `docs/21 §18.4`。
> 把它写在这里是因为它属于同一条纪律：**升级必须重跑全部证据链**，
> 而重跑的价值不仅是确认没坏，也包括发现"原来的验证其实没测对"。

## 8. 已知边界（诚实清单）

1. **扫描覆盖的是"已知"漏洞**：OSV 收录范围之外的问题扫不出来；
   0 条漏洞的含义是"没有已知漏洞"，不是"没有漏洞"。
2. **Python 侧按实际安装版本扫描**：若运行环境与开发环境不同，需在**交付环境**重跑扫描。
3. **Maven 只扫 dg-api 的运行时树**：`dg-sdk` 作为对外 SDK 单独发布时需要独立扫描。
4. **未接入 SBOM 生成**：当前证据是 JSON 报告；要做到客户可直接消费，
   还需补 CycloneDX/SPDX SBOM（已列入待办，未实现）。
5. **未接入签名与来源验证**（`mvn` 的 GPG 校验、npm 的 provenance 校验）。
6. **未做企业私有仓库镜像的落地配置**：公司合规环境通常要求离线/内网仓库，
   本文件只把它列为选型标准（§4 第 8 条），具体镜像方案需按部署环境落实。
7. **Spring Boot 4.x 迁移未做**：本轮选择 3.5.x（3.x 线最新补丁）。
   4.x 涉及 Spring Framework 7 / Jakarta 世代变更，属于**独立的一次升级项目**，
   需要单独评估与回归，不应与漏洞修复混在一起做。
8. **豁免台账当前为空**：本轮所有发现都通过升级/替换/删除解决，**没有使用任何豁免**。
   台账为空是好结果，但机制本身必须留着（否则下次就只能口头承诺）。

## 9. 需要业务方/安全团队确认的事项

1. 修复时限（7 / 30 / 90 天）是否与公司既有安全基线一致？如需更严（例如 HIGH 也要求 7 天），
   需要相应调整发布节奏；
2. 是否要求**交付 SBOM**（CycloneDX/SPDX）与签名验证？这决定 §8 第 4/5 条的实施优先级；
3. 是否要求**离线/内网镜像**（涉及构建流水线改造）；
4. 合规证据的**留存期限**与归档位置（当前报告在 `security/reports/`，未纳入版本库）。
