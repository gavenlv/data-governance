# 11 · 路线图与 MVP 定义

> 状态：Draft v0.1
> 核心原则：**先让人用起来，再让人管起来。** 治理平台的价值曲线是"发现 → 理解 → 信任 → 管控"，跳步必死。

---

## 1. MVP 边界（最重要的一节）

自研治理平台最大的风险是范围失控。因此 MVP 用"一个必须做成的故事"来定义：

> **故事**：一名数据分析师被问"我们的 GMV 口径是什么、数据从哪来？"。
> 他在平台上搜到指标与术语定义 → 打开资产页看到 Owner、描述、分级、质量状态 → 点开血缘看到从 ODS 到报表的完整链路与转换逻辑 → 一键联系 Owner 或**发起访问申请（走审批流）**。
> **全程不超过 3 分钟，且信息可信。**

> ⚠️ **范围澄清（来自 `19` 独立评审 B3）**：上面这句必须读准——MVP 交付的是"**申请与审批流程**"，**不是"权限自动生效"**。MVP 阶段审批通过后产出的是一张**授权工单/审批凭据**，真实数据访问仍由现有 DBA/权限流程实施（这就是 ADR-008 的降级形态：策略导出 + 人工实施 + 合规校验）。
> 如果这一点不写清楚，用户点完申请后发现自己仍读不到数据，就会直接摧毁信任——而这正是本方案列出的头号风险"无人使用"。
> **要在 MVP 就做到"审批通过即生效"的唯一办法**：把策略下发到**至少一个引擎（首选 Trino `SystemAccessControl` + `ConnectorAccessControl` 的行过滤/列脱敏）**提前进 MVP——这是一个需要业务方明确拍板的取舍（见 `12` ADR-008 的复审触发与 `19` §一 B3 的两个选项）。

为了做成这个故事，MVP 必须有：采集（至少核心源）、统一模型、搜索、资产详情、表级+列级血缘、术语表、标签分级、Owner、权限、协作。**没有一样是"锦上添花"。**

### MVP 明确不做（防止范围蔓延）
- 不做质量规则引擎（只做剖析 + 展示源系统已有的质量结果）
- 不做契约 CI 门禁（先把契约当文档级能力，v2 才接 CI）
- 不做策略下发到查询引擎（只做平台内权限 + 访问申请）
- 不做异常检测 ML、不做数据市场、不做 AI 生成描述（只做 NL 搜索）
- 不做跨租户联邦、不做 MDM

### 1.1 采集路径的战略选择（先定策略，再排连接器）

来自 `research/03` §7.7 的判断：商业侧的元数据来源只有三条路径，**自研应优先组合 (a)+(b)，而不是重造 (c) 的连接器矩阵**——连接器广度是 2–3 年社区累积的结果，自研在此维度投入产出比最低。

| 路径 | 覆盖 | 成本 | 我们的用法 |
|---|---|---|---|
| **(a) 查询日志驱动**（引擎 query history / BI 审计日志） | 广、零人工改造 | 低（只需读取权限） | **v1 主力**：一次接入即获得血缘（表级为主）+ 使用热度 + 共现关系；受日志保留期限制，需显式标注覆盖边界 |
| **(b) dbt / manifest 驱动**（编译期元数据） | 只在 dbt 世界内有效 | 极低（读产物） | **v1 主力**：编译期血缘最准，且与契约/测试天然同源 |
| **(c) 连接器/元数据驱动**（逐源适配） | 通用 | 高（长期维护矩阵） | **白名单 + 复用开源实现**：只对核心源做一流体验，其余按需共建 |

由此对下面 Phase 1 的"连接器扩至 15+"给出明确口径：**不是自己从零写 15 个连接器，而是"白名单内核心源自研/精修 + 其余复用移植 OpenMetadata/DataHub 的 Apache-2.0 实现 + 框架适配层"**（见 `10` §1 与 `12` 第一部分）。

> ⚠️ **两处必须澄清（来自 `19` 独立评审 B2 与事实项 8）**：
> ① **"复用/移植"不是零成本**：OpenMetadata 的连接器是 Python 实现，若控制面是 Java，正确说法是"**参考其采集逻辑与字段映射，在我们的框架内重写**"，或"以 Python 侧车承载其实现"。**不要按"直接拿来用"排期**。
> ② **"可移植"这一判断本身依赖一项待核实事实**：OpenMetadata 的 OSS 与 Collate 商业版功能边界**未逐项确认**（`research/README` §5 列为 🔴）。因此"复用其连接器"必须标注为**待许可与边界核实后的计划**，不是既成结论。

## 2. 阶段规划（以"可用"为里程碑，而非"功能完成"）

时间以 **3–4 人核心团队**（统一口径，见 §4；`19` 独立评审 B2 指出本节曾写"2–3 人"与其它文档的"3–4 人"冲突，此处已统一）+ 兼职支持估算；人力翻倍可压缩约 40%（非线性的，因为治理平台的瓶颈是设计决策而非编码）。**另有运维/SRE 0.5–1 人**（见 §4），全案此前未指定运维归属，这是被评审点名的缺口。

### Phase 0 · 地基（0–2 月）
| 交付 | 验收标准 |
|---|---|
| 元数据模型 v1（实体/aspect/edge + Model Registry 雏形） | 模型 YAML 可生成 Java/Python/TS 客户端；兼容性 CI 生效 |
| 元数据核心服务（PG 真相源 + 版本 + 审计 + outbox 事件） | 事件可重放重建搜索索引；并发写不互相覆盖（乐观锁测试） |
| 采集框架 + 4 个连接器（MySQL、PostgreSQL、Hive/HMS、Trino） | 增量采集、状态存储、错误不产生脏数据、人工编辑不被覆盖 |
| 搜索 + 基础 UI（搜索页、资产详情页、Schema 浏览） | **MVP 验收规模 = 灯塔域实际规模（约 10 万实体）**；并须证明在 **v1 适用范围上限（500 万实体，见 `07` §3.2）** 下仍满足 P95 < 500ms——**两级验收**（`19` 评审事实项 3：此前只验收 10 万，"验收标准选得太舒服"） |
| 认证（OIDC）+ RBAC + **tenant 列（v1 不启用 RLS）** | SSO 登录、租户列隔离正确；**RLS 推迟**（`19` 评审过度设计项 2：RLS 会污染每条 SQL、索引与缓存键，而灯塔域只有一个租户） |
| 部署（docker compose + 初步 Helm） | 一条命令起单机版；生产版可 K8s 部署 |

**Go/No-Go 检查点**：模型稳定性（后续 5 个 aspect 新增不改核心代码）、采集幂等性、事件重放可用。

### Phase 1 · 目录可用 + 血缘（2–5 月）
| 交付 | 验收标准 |
|---|---|
| 连接器：**白名单核心源 5–8 个**（如 MySQL、PG、Hive/HMS、Trino、dbt、Airflow、ClickHouse）+ 其余按需共建 | 覆盖灯塔域全部数据源；**Kafka/BI/S3 等延后**（`19` 评审 B2：原"15+"在 3 个月内不现实，且与"复用≠零成本"冲突） |
| 血缘引擎：**表级为主 + 列级仅覆盖 dbt/SQL 主路径**；OpenLineage 端点 + 采集查询日志 | 表级血缘覆盖率 ≥ 80%；列级仅在 dbt/SQL 主路径上承诺 ≥ 90%（按方言报告）；解析失败**必须显式降级并落异常样本库** |
| 血缘可视化 + 影响分析（3 跳内 P95 < 1s） | 1000 万边基准 |
| 术语表 + 词条映射 + 标签/分类分级 + Owner 管理 | 术语可与资产双向关联；搜索同义词生效 |
| 自动 PII 识别 + **列级标签传播** | 传播正确率与冲突显性化（人工抽检 ≥ 90%） |
| 协作：评论/@提及/订阅/待办中心 + IM 通知 | 关键变更 5 分钟内到达 IM |
| 资产健康分 v1 + 治理 KPI 看板 v1 | 分数可解释（每项扣分可点击定位） |
| **采纳度指标** | 周活用户 ≥ 目标用户 40%；搜索成功率 ≥ 60% |

**Go/No-Go**：血缘可信度是否被业务方接受（抽查 20 条链路，人工确认 ≥ 85% 正确）。

### Phase 2 · 质量与契约（5–9 月）
| 交付 | 验收标准 |
|---|---|
| 剖析（采样统计、直方图、Top-K）+ 结果趋势 | 采样成本可控（单表默认 ≤ 10k 行） |
| 质量规则引擎（YAML + SQL + dbt tests 三前端，统一 IR）+ 调度 + 结果留痕 | 规则可推到源系统执行；误报可控 |
| 数据契约（ODCS 兼容）+ 版本 + 兼容性 diff + 违约事件 | 契约可生成质量规则；违约定向通知消费者 |
| CI 插件（GitHub/GitLab）+ 血缘影响 PR 评论 | PR 上能看到"受影响下游清单" |
| SLO + 事故管理 + 根因关联（血缘 + 质量联动） | 一次真实故障完整走通 Timeline → Postmortem → 新增规则 |
| 数据可观测性 v1（季节性基线异常检测） | 误报率 < 10%（业务方确认） |

### Phase 3 · 策略与联邦（9–14 月）
| 交付 | 验收标准 |
|---|---|
| 访问申请审批工作流 + 授权引擎（RBAC+ABAC+层级继承，细粒度关系授权可选引入 OpenFGA）+ 到期回收 | 审批 SLA 可统计；到期自动回收率 100% |
| **策略编译器 + 下发**（Trino/Spark 行过滤与列掩码、数仓原生策略） | 快照测试全覆盖；灰度下发 + 失败回滚 |
| Domain / Data Product 一等公民 + 域记分卡 | 每个域有 Owner、SLO、契约；记分卡进入季度评审 |
| 分类分级合规映射 + DSAR 支撑 + 审计报告导出 | 一次合规审计用平台自证 |
| 血缘规模升级（派生图库，**当规模越过 `07` §3.2 的 1 亿触发点，或 Spike S2 实测不达标时**） | 在 ≥1 亿边规模下 5 跳查询 < 3s；**若长期在 5000 万边以内则本项不交付**（`19` 评审 B1：此项此前写成无条件交付，与设计适用范围矛盾） |

### Phase 4 · AI 与开放生态（14–18 月）
| 交付 | 验收标准 |
|---|---|
| 语义/向量混合检索 + NL 问答（带引用） | 回答必须给出来源资产链接；无据不答 |
| AI 建议引擎（描述/标签/术语映射/血缘推断）+ Suggestion 收件箱 | 建议采纳率 ≥ 40%；全部带 provenance |
| MCP Server / Agent 工具集 | 外部 Agent 可安全访问（权限裁剪生效、审计完整） |
| 嵌入式 Widget（BI/IDE 内展示治理信息） | 至少 2 个 BI 工具集成 |
| 指标/语义层元数据接入（dbt Semantic Layer / Cube） | 指标口径可追溯到物理列 |
| 开放连接器 SDK（第三方可开发连接器） | 外部团队开发的连接器可无侵入加载 |

## 3. 组织与采用路径（技术之外的成败关键）

治理平台的失败 80% 是组织问题。方案必须包含"人"的部分：

### 3.1 角色与职责
| 角色 | 职责 |
|---|---|
| 平台团队（3–6 人） | 平台建设与运维、连接器、模型演进 |
| 数据治理委员会（虚设但要有） | 分级标准、术语审批、争议裁决、KPI 评审 |
| 域数据管家（每域 1 人，兼职） | 本域资产健康分、术语、分类复核、血缘确认 |
| 数据 Owner（每资产） | 描述、质量规则、契约、访问审批 |
| 平台运营（关键角色，常被忽略） | 推动采纳、培训、处理待办、发布治理周报 |

### 3.2 采用路径（先窄后宽）
1. **选一个"灯塔域"**：选一个数据使用频繁、痛点明确、Owner 配合的域（不要选最大最复杂的域）。
2. **用真实场景驱动**：不用"请来填元数据"，而是"在线故障排查"、"新同学找数据"、"合规检查准备"这类具体任务。
3. **让平台出现在工作现场**：IM 机器人、CI 评论、BI 嵌入查询入口——不要指望用户主动登录。
4. **度量并公开**：域记分卡公开排名（配合正向激励，避免变成批斗）。
5. **再横向扩展**：灯塔域成功后复制（含连接器、模板、规则库），而非一次性全公司铺开。

### 3.3 采纳度的硬指标（写入 KPI）
| 指标 | 目标（上线 6 个月） |
|---|---|
| 核心资产覆盖率（有 Owner + 描述 + 分级） | ≥ 70% |
| 血缘覆盖率（关键链路已登记） | ≥ 80% |
| 周活跃用户 / 目标用户 | ≥ 40% |
| 搜索成功率（点击并停留 > 10s 的比例） | ≥ 60% |
| 治理待办关闭率（30 天内） | ≥ 70% |
| 因元数据缺失导致的沟通成本下降 | 主观调研 + 支持工单量趋势 |

## 4. 资源与成本概览（量级估算，非报价）

| 项 | 说明 |
|---|---|
| 人力 | 核心 3–4 人（1 架构 + 2 后端 + 1 前端），前端在 Phase 1 起需全职；Phase 2 起加 1 名数据/质量方向与 1 名 AI 方向 |
| **运维/SRE** | **0.5–1 人（专职或固定分配，不可"兼职顺手做"）**。负责：PG 主从与备份恢复、OpenSearch 索引与容量、Kafka、Helm/升级回滚、SSO/SCIM、监控告警、漏洞修复与依赖升级、恢复演练。**`19` 独立评审 B2 指出：本方案此前从未指定运维归属——这是投产即爆的缺口。** |
| 时间 | MVP（Phase 0+1）约 5–6 个月到"亮点域可用"；完整能力（到 Phase 3）约 14 个月 |
| 基础设施 | 标准版约 8–16 核 CPU / 32–64 GB（PG + OpenSearch + Kafka + API/Worker），单机版 4 核 / 16 GB |
| 外部依赖成本 | LLM API（AI 阶段，按 token 计费，需配额与缓存）、向量与搜索存储 |
| 隐性成本 | 连接器长期维护（每条源系统版本升级都要跟）、升级与迁移支持、客户环境差异支持——**这部分常被低估 2–3 倍** |

## 5. 里程碑风险与退出条件（提前写好"什么时候该停"）

| 风险信号 | 触发条件 | 应对 |
|---|---|---|
| 模型反复推翻 | 同一 aspect 结构改 > 3 次且影响面大 | 暂停功能开发，先做模型稳定性设计与评审 |
| 血缘可信度不达标 | 抽查正确率 < 70% | 收敛范围到"运行时上报 + 关键链路"，放弃全量静态解析野心 |
| 无人使用 | 上线 3 个月周活 < 20% | 停止新功能，转做"现场嵌入 + 灯塔场景"，否则考虑转向二开开源 |
| 连接器维护失控 | 单次源系统升级导致 > 20% 连接器需修改 | 抽象连接器版本兼容层；限制支持源系统清单 |
| 性能不达标 | 搜索/血缘延迟超 SLO 2 倍 | 提前启用派生图库与索引分片方案（已在架构中预留） |
| 与既有平台重复 | 公司已部署 OpenMetadata/DataHub 且满意度尚可 | **诚实地重新评估 build vs buy**（见 `12`） |

## 6. 与"直接二开开源"的对照时间线（决策参考）

| 方式 | 6 个月能到哪 | 优势 | 代价 |
|---|---|---|---|
| 直接用 OpenMetadata | 目录 + 血缘 + 质量基本可用（配置 + 少量开发） | 极快见效、连接器最多 | 深度定制受限、数据面策略无法执行、AI/合规能力受限 |
| 用 DataHub + 二开 | 目录 + 血缘聚合强、扩展模型强 | 事件模型优雅、社区活跃 | 运维复杂、模型扩展需 PDL+Java 重部署、升级成本高 |
| **本方案（自研内核 + 复用生态件）** | MVP（Phase 0+1）可点亮一个域 | 完全可控、可做策略执行与差异化、可真联邦 | 前 6 个月没有"成品"，人力投入最高，连接器从零积累 |

> 这条对照必须交给决策层看：**自研是在为"未来 3 年的差异化与可控性"付"当下 6–12 个月的效率"**。如果业务不接受这个交换，就应该二开而不是自研。
