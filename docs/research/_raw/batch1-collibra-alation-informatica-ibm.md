### 差异化所长（最有价值的一个设计）

**可配置 Operating Model + 内置工作流引擎的组合**：把「治理对象」本身变成用户可定义的一等模型（自定义资产类型 / 关系类型 / 社区 / 域 / 责任 / scope 规则），而不是固定 schema；再叠加通用多步审批工作流。这在自建平台上是最难复刻的部分——它本质上是**治理元模型 + 流程引擎**，而非某个功能页。对比参照物（Atlan 等）多把模型写死，Collibra 让企业把自身的治理章程「编译」进平台。

### 差异化所长（最有价值的一个设计）

**查询日志驱动的 Behavioral Analysis（行为分析）**。Alation 把数仓/BI 的 **query log 作为一等元数据源**摄取进 Active Metadata Graph，从而得到两件别家很难做的事：(1) 基于**真实使用频次**的搜索排序与「热门资产」；(2) 由使用行为**反推**该给谁派 Steward、哪些资产值得优先治理。这把「治理」从人工盘点变成**数据驱动的人口普查**。对自建平台的启示：若元数据库里没有 usage/query 事件的时序建模，就无法复刻这一层。

### 差异化所长（最有价值的一个设计）

**治理与数据搬运在同一平台内闭环 —— CLAIRE 贯穿 + 策略在数据管道内执行**。两条硬证据：

1. **CDGC 的知识图谱跑在 Amazon Neptune 上**——AWS 官方博客专文《How Informatica Cloud Data Governance and Catalog uses Amazon Neptune for knowledge graphs》公开了其图存储选型（[AWS Database Blog](https://aws.amazon.com/cn/blogs/database/how-informatica-cloud-data-governance-and-catalog-uses-amazon-neptune-for-knowledge-graphs/)）。这是本批次四家中**唯一被官方公开确认的图数据库选型**。
2. **CDAM 的访问策略在 Cloud Data Integration 内部被物理执行**——CDI 转换文档中出现 `_cdam_` 前缀的注入列（[CDI 转换文档](https://docs.informatica.com/content/dam/source/GUID-2/GUID-2B5E2342-3D75-4BCE-B092-A78F85631717/68/en/CDI_July2025_Transformations_en.pdf)、[知识库说明](https://knowledge.informatica.com/s/article/000246110)）。即：**策略不是「记录在目录里」，而是被编译进实际的数据流**。这解释了为什么 Informatica 的治理比纯目录产品「更硬」，也是自建平台最难对标的一环——需要平台同时拥有数据搬运能力。

### 差异化所长（最有价值的一个设计）

**Manta 的「自动」血缘——靠解析代码/脚本/字节码自动连边，而非人工映射**。可确证机制（全部来自官方 Manta 文档）：

- 自动解析 **DDL 脚本**：「By default, Maria Flow **extracts DDL scripts** from configured MySQL, MariaDB, or SingleStore servers and then analyzes their data…」
- 自动解析 **存储过程**：将 **Db2 PL/SQL 脚本**放入 `<MANTA_DIR_HOME>/input/db2/` 即可分析
- **列级**追踪可经代码注解锚定：「source column → **@MANTALineage** annotation → mapping → source attribute」
- **Java / C# 应用级扫描器**有独立学术论文描述其调用上下文数据流分析（Parízek & Hermann, ICSE-SEIP 2024，《Data Lineage Analysis for Enterprise Applications by Manta: The Story of Java and C# Scanners》）（[论文 PDF](https://d3s.mff.cuni.cz/files/public/parizek/pubs/icse24-seip.pdf)、[IEEE CSDL](https://www.computer.org/csdl/proceedings-article/icse-seip/2024/050100a025/1XSoeRCeiRi)）
- （[以上均见 Manta Data Lineage 官方文档 PDF](https://www.ibm.com/docs/en/SSFQYQB/pdf/manta-data-lineage-documentation.pdf)）

这一路径与 Informatica「Scanner + AI 推断」、Collibra「harvester + stitching」形成鲜明对比：Manta 更接近**静态代码分析（SAST 思路）**，因此在 ETL 脚本/存储过程密集的传统数仓环境里覆盖率高、且**不依赖运行时流量**。对自建平台的启示：如果只做 SQL 解析，会漏掉存储过程、Java 批处理与报表层，这是 Manta 的护城河。
