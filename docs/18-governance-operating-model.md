# 18 · 治理制度与运营模型（Operating Model）

> 状态：Draft v0.1
> 平台是工具，制度是骨架。**平台上线前必须先定制度，否则平台只会放大混乱。**
> 本文提供可直接改造使用的模板：责任矩阵、分级标准、术语治理流程、质量门禁、事故响应、考核挂钩。

---

## 1. 责任矩阵（RACI）

| 活动 | 数据治理委员会 | 平台团队 | 域 Data Steward | 资产 Owner | 数据用户 | 安全/合规 |
|---|---|---|---|---|---|---|
| 分级标准制定 | **A** | C | C | I | I | **R** |
| 术语审批 | **A** | I | **R** | C | C | I |
| 资产登记与描述 | I | C | **A** | **R** | C | I |
| 质量规则定义 | I | C | C | **R/A** | C | I |
| 数据契约签署 | I | C | C | **R**（生产方） | C（消费方 C） | I |
| 分类分级复核 | I | C | **R/A** | C | I | C |
| 访问审批 | I | I | C | **R/A** | **R**（申请方） | C |
| 事故响应 | I | C | C | **R/A** | I | C |
| 合规审计 | **A** | C | **R** | C | I | **R** |
| 平台建设与运维 | I | **R/A** | C | I | I | C |
| 治理 KPI 评审 | **A** | **R** | C | C | I | C |

（R 执行 / A 负责 / C 咨询 / I 知情）

**关键点**：每个资产必须有唯一的 **A（Accountable）**，且是**具体的人**而非"某团队"。无主资产必须进待办。

## 2. 数据分级标准模板（可配置）

| 级别 | 名称 | 判定 | 示例 | 默认控制 |
|---|---|---|---|---|
| **L1** | 公开 | 可对外发布 | 已发布的公开报表、公开 API | 无需审批，允许导出 |
| **L2** | 内部 | 全员可见，不得外传 | 内部经营看板、产品埋点聚合 | 登录可访问，导出留痕 |
| **L3** | 敏感 | 限定范围，含个人信息或商业敏感 | 客户手机号、订单明细、成本数据 | 需申请审批、默认脱敏展示、导出需二次审批、访问审计 |
| **L4** | 机密 | 极小范围，泄露后果严重 | 身份证号、银行卡、核心算法参数、未公开财报 | 强审批 + 双人复核 + 强制脱敏 + 定期复核 + 禁止批量导出 |

规则：
- 分级**可继承**（表级 → 列级取最高；血缘向下游传播，见 `09` §9.6）；
- **冲突取更严格**，并生成复核任务；
- 未分级资产默认按 **L2** 处理（保守默认，且计入健康分缺口）；
- 分级变更必须留痕并通知已授权用户与下游 Owner。

## 3. 术语（Glossary）治理流程

```
提出（任何数据用户）→ 域 Steward 初审（是否与已有术语重复/冲突）
  → 若为跨域术语 → 提交治理委员会评审（季度会 + 紧急通道）
  → 通过 → 登记术语（定义、口径、公式、Owner、同义词、关联资产）
  → 平台自动：建立与物理资产的映射链接、进入搜索同义词、通知订阅者
  → 变更 → 走同样流程 + 影响面通知（引用该术语的资产/报表/指标）
```
规范：
- 一个术语必须有**唯一 Owner**与**一句可验证的定义**（禁止"泛指/相关/等"这类词）；
- 术语必须有**同义词与反例**（"什么不算"），这是区分于"字典"的关键；
- 指标类术语必须给出**计算公式与数据来源资产**（可追溯）；
- 术语不允许多个近义术语并存（重复 → 合并，不新增）。

## 4. 质量门禁规则（示例，按资产等级分档）

| 资产等级 | 必填治理属性 | 质量要求 | 门禁位置 |
|---|---|---|---|
| L1/普通报表 | Owner、描述 | 无强制 | 无 |
| L2 | Owner、描述、分级、至少 1 条新鲜度规则 | 通过率 ≥ 95% | 发布时提醒 |
| L3 | 上述 + 术语映射 + ≥ 3 条质量规则 + SLO | 通过率 ≥ 99%，告警响应 ≤ 1h | **CI 阻断**（新表/新变更） |
| L4 | 上述 + 契约 + 访问策略 + 保留期 + 定期复核 | 通过率 100%，告警响应 ≤ 15min | **CI 阻断 + 双人审批** |

配套：**豁免机制**（带到期时间与审批人，禁止永久豁免）；豁免率进入治理 KPI（豁免过多的规则本身需要修订）。

## 5. 事故响应流程（与数据可靠性对齐）

```
发现（监控告警 / 用户上报 / 采集违约）
  → 自动分级（影响面 × 分级 × 是否对外）
  → 建 Incident（平台内）+ 通知 OnCall（IM）
  → 止血（如暂停下游作业、切换备用表）
  → 根因（血缘回溯 + 质量结果 + 运行日志）
  → 恢复验证（质量规则重跑）
  → Postmortem（模板化，72 小时内）
  → **必产出**：新增/修订至少一条质量规则或检测器（否则事故会重复）
  → 归档并更新资产健康分与 SLO
```
分级参考：S1（对外/合规/大面积，15 分钟响应）→ S4（局部，次日处理）。

## 6. 考核与激励挂钩（决定治理能不能持续）

| 对象 | 指标 | 挂钩方式 |
|---|---|---|
| 域 / 团队 | 资产健康分均值、SLO 达成率、待办关闭率、契约覆盖率 | 季度数据治理评审；纳入团队 OKR（权重建议 5–10%，不宜过高以免造假） |
| 数据管家 | 待办关闭率、术语与分级复核及时率 | 计入个人职责（建议给工时配额，如每周 4 小时） |
| 平台团队 | 采用度（周活、搜索成功率）、平台可用性、采集健康 | 平台自身的 OKR |
| 数据用户 | 无（不对使用者考核，避免"不敢用数据"） | 只做正向激励（贡献术语/描述给予认可） |

**反作弊设计**：健康分不只看"填了没有"，还看描述被查看/引用次数、被 AI 判定为"空话"的比例；批量灌水会被识别并降权。

## 7. 平台自身也需要治理（不搞双重标准）

| 项 | 要求 |
|---|---|
| 元数据本身的敏感度 | 资产名称、Schema、Owner 信息本身也可能敏感 → 平台自身要做分级与访问控制 |
| 平台 SLO | 明确可用性与延迟目标（见 `07` §8），公开给用户 |
| 变更公告 | 平台破坏性变更需提前公告 + 迁移指南（**自己都不做，凭什么要求业务做**） |
| 平台审计 | 谁在平台里做了什么（含 AI 调用）全留痕 |
| 数据保留 | 采集快照、剖析样本、AI 上下文的保留期明确且可配置 |

## 8. 上线检查清单（制度侧，Go-Live Gate）

- [ ] 治理委员会成立且有章程（决策范围、频率、升级路径）
- [ ] 每个域指定 Data Steward，并给出工时配额
- [ ] 分级标准发布（含 L3/L4 判定示例与常见歧义处理）
- [ ] 术语治理流程发布，且已有 3 个真实术语走完全流程（试运行）
- [ ] 质量门禁规则发布，并明确豁免流程与审批人
- [ ] 事故响应流程与 OnCall 对齐（含 IM 群与升级路径）
- [ ] KPI 定义与考核挂钩方案获管理层认可
- [ ] 灯塔域选定，且其 Owner 明确承诺参与
- [ ] 用户培训与"如何提问/如何反馈"渠道就绪
- [ ] 退出条件与复盘节奏确定（月度运营复盘、季度成熟度评估）
