# 19 · 独立评审报告（Independent Architecture Review）

> 评审人立场：以 CTO 视角做**对抗性评审**，目标是找缺陷而非确认方案。
> 评审依据：`docs/00`–`18` 与 `docs/research/01`–`05`（含 `research/README.md` 的可信度声明）。
> 凡标注「不确定」处，均为评审人无法从文档或调研底稿证实、需在 Spike 或法务环节补证的项。

---

## 一、致命问题（Blocker）

### B1. 图存储方案与自报 SLO 规模自相矛盾，血缘闭包行数量级从未估算

**问题**：`07` §3.2 声明 v1 适用规模是"节点 < 100 万，边 < 500 万"，图库推迟到 v2；但 `07` §8 的 SLO 验证规模写的是"**千万级实体 / 亿级边**"，`11` Phase 3 更要求"**亿级边 5 跳查询 < 3s**"。更严重的是 `09` §9.2 自定的图库引入触发条件之一是"**节点+边超过约 1 亿**"——按方案自己的规则，v1 的 SLO 验证规模已经越界，图库不再是"v2 可选"。

**证据**：`07` §3.2 v1/v2 分界表；`07` §8 规模口径说明；`11` §2 Phase 3 验收标准；`09` §9.2 三个触发条件。

**影响**：这不是"留 5–10 倍余量"能解释的（`07` §8 注脚如此辩解），而是**同一份方案里存在两个互斥的架构前提**：按 500 万边设计，则 SLO 压测无意义；按 1 亿边设计，则 PG 边表 + 物化闭包从未被验证。连带 `10` §3.1 只算了 Aspect 的 18GB，**没估 `lineage_closure_mv` 的行数**，而 1–3 跳可达对在宽扇出拓扑下会组合爆炸（`09` §9.2 自述"最坏 O(V²)"）。

**修改建议**：① 把"架构适用范围"与"SLO 验证规模"统一为一组数字并写进 ADR-003；② Spike S2 增加硬指标：`depth≤3` 闭包在**真实拓扑（含宽扇出）**下的行数与刷新耗时，超阈值即改走"预计算关键路径 + 域级聚合图"；③ 若确认目标为亿级边，把派生图库上移到 v1 交付清单——"实测再说"是无法排期的表述。

### B2. 工期、人力与交付范围三者不自洽，且没有运维/SRE 编制的归属

**问题**：`11` §2 明确"时间以 **2–3 人**核心团队估算"，而 `00` §0、`12` Q4、`17` §4 档位 C 写的都是 **3–4 人（至 3–6 人）**。`11` Phase 1（2–5 月，**3 个月**）要交付：连接器扩至 15+、列级血缘（真实语料成功率 ≥90%）、列级分类传播、术语表、协作+待办中心+IM、健康分+KPI 看板；`16` §3 又要求 CI 插件、IM、查询引擎日志三个集成"**MVP 就要**"。

**证据**：`11` §2 表头与 Phase 1 交付表；`00` §0/§10.7；`12` §2 Q4；`17` §4 档位 C；`16` §3。

**影响**：`11` §1.1 已诚实承认"连接器广度是 2–3 年社区累积的结果"，但 Phase 1 仍把 15 个连接器塞进 3 个月；`09` §9.1 的落地方案是"移植 OM（Python）与 DataHub 的实现 + 自研框架适配层"——**把 Python 连接器翻译进 Java 框架不是复用，是重写**，这部分工作量在排期里被隐藏。此外，生产形态需要 PG 主从、OpenSearch、Kafka、Redis、Helm、备份恢复、升级回滚、SCIM/SSO、漏洞修复，而**全方案没有任何一处标明谁做运维**（`11` §4 只列了核心 3–4 人 + 前端 + 质量 + AI）。

**修改建议**：① 统一人力口径，在 `11` §4 明确运维由谁承担（专职或固定 0.5–1 人力）；② Phase 1 砍到"5 连接器 + 表级血缘 + 列级仅 dbt/SQL 主路径"——这正是 `17` §4 档位 B 已给出的答案，方案却没采纳它来修正 Phase 1；③ Phase 1 延到 6 个月，或把"周活 ≥40%"后移到 Phase 2。

### B3. MVP 的核心故事承诺了一个它明确不交付的能力

**问题**：`00` §6 与 `11` §1 把 MVP 定义为"分析师 **3 分钟内**找到 GMV 定义、来源链路与负责人，并**申请到访问权限**"；但 `11` §1"MVP 明确不做"第一条就是"**不做策略下发到查询引擎（只做平台内权限 + 访问申请）**"。

**证据**：`00` §6、`11` §1 故事 vs `11` §1 不做清单；`07` §2 把 7.3 策略编译下发标为 P2；`09` §9.7 与 `research/05` §(引擎) 指出执行点必须落在 Trino `SystemAccessControl` / Spark Connect 等**查询路径**上，BI 层"只作消费端，不进执行路径"。

**影响**：MVP 阶段的"申请到访问权限"只能产出一张审批单，**不产生真实数据访问权**。用户点完申请发现自己仍读不到数据，还要去提人工工单——`00` §8 把"无人使用（3 个月周活 <20%）"列为头号风险，而这个设计恰好制造它。更讽刺的是 `12` §4.1、`17` §5 反驳六都认定"策略执行"是**唯一自研理由**，它却排在 9–14 月。

**修改建议**：二选一——① MVP 故事改为"找到定义、链路、负责人，**发起审批**"，并写明数据访问生效仍由现有工单流程完成；② 或把"审批通过后至少一个引擎（Trino）授权自动生效"提前进 MVP，哪怕只做 `12` ADR-008 已有的降级形态（策略导出 + 人工实施 + 合规校验）。

## 二、事实性错误与自相矛盾

1. **图库触发阈值口径不一**：`09` §9.2 与 `research/04` 用"节点+边超 1 亿"，`10` §1、`07` §3.2 却只提"亿级边"。需统一。
2. **血缘解析选型与调研结论冲突且未标注**：`research/04`（正文+附录）的选型是"**sqlglot 主 + Calcite 对核心数仓层二次校验**"，理由是有校验器才能发现 `SELECT * FROM a JOIN b` 同名列歧义；`10` §1 只列 sqlglot 并称 JVM 方案"远弱"，`12` §3 写"直接复用 sqlglot"，而 `15` Spike S1 又保留双解析器对比。**调研结论到设计层被静默丢弃**——`12` ADR-009 处对"调研分歧"是有记录习惯的，这里漏了。
3. **搜索规模口径不一致**：`11` Phase 0 的搜索验收是"**10 万实体**下 P95 <500ms"，`07` §8 的读延迟验证是"**千万级实体**"。两者都对，但方案没说 10 万→千万的拐点在哪、拐点处要改什么，属"验收标准选得太舒服"。
4. **`09` §9.2 的置信度融合公式有统计缺陷**：`confidence = 1 - Π(1 - c_i·w_i)` 隐含**来源条件独立假设**，而静态解析/查询日志/运行时上报高度相关，会系统性高估置信度。方案只写了"同族取最大值"，未定义"同族"边界，也未给相关性折减系数。建议改为带折减的形式，并在 Spike 中用真实数据拟合 w_i。
5. **AI 基准结论过度外推**：`13` §1.1 称"Spider 2.0 与 BIRD 上 SOTA 仅 70% 量级"。`research/04-standards-and-tech-appendix.md` 的实际表述是 Spider 2.0 成功率"**远低于 Spider 1.0**"，"70%+"是 **BIRD** 的数字。把 BIRD 的数字挂到 Spider 2.0 上属误述；该附录还有一条"Text-to-SQL 基准存在普遍标注错误"的免责，`13` 未继承。（不确定：是否需要精确数字，但不应同时挂两个基准。）
6. **ODCS 版本在文档内不一致**：`06` §1.1 写"v3.2.0（2026-09）"，`08` §7.2 写"v3.1.0 起可隐式推导"，`research/03` 结论区仍以"**v3.1.0** 为格式基准"。同一方案对"兼容哪个版本"没有唯一答案，直接影响 `08` §7.2"apiVersion 与 version 必须分开治理"能否落地。
7. **Soda Core 的 ELv2 变更时点两说**：`10` §4 写"自 **2026-01** 起 ELv2"，`research/05` 写"自 **v4** 起"，`10` §9.4 又写"2026-01"。三者需收敛，否则 SCA 规则无法写。
8. **"连接器可移植"的结论强于底稿**：`09` §9.1、`12` §3 直接称可移植 OM/DataHub 的 **Apache-2.0** 实现。许可判断本身正确（`research/01` §1.3、`research/02` 许可），但 `research/README` §3 与 `research/05` 待核实清单明确指出 OM 的 **OSS vs Collate 边界未逐项确认**、"异常检测是否全部随免费自托管版发布"为 🔴 未核实。设计正文不应把「待核实」当既成事实。
9. **优先级与差异化理由倒挂**：`12` §4.1、`17` §5 反驳六把自研理由**收敛为 D7（策略执行）+ D8（治理运营）**；但 `07` §2 把 7.3 策略编译下发标为 **P2**、8.2 域记分卡标为 **P2**，而把公认"赢不了开源"的 2.1 搜索 / 2.2 资产页标为 P0。`17` §1 错误 1 担心的"把功能清单当路线图"在此处实际发生了。

## 四、关键遗漏

1. **钱从哪来、怎么证明值**：`11` §4 只有"量级估算，非报价"，全文无金额、无预算科目、**无与采购/二开路线的 5 年 TCO 对比表**。`12` §1.1 诚实指出"云市场承诺额度可核销"是自研无法享有的优势，却没换算成钱（不确定：具体金额取决于人力口径，方案未给）。**没有 TCO 对比与 ROI 基线，这笔预算无法在财务评审中通过。**
2. **ROI 的证明方式缺失**：`11` §3.3 的周活、搜索成功率是**产品指标不是投资回报指标**。需要的是"审计准备时间从 X 天降到 Y 天""重复取数沟通工单下降 Z%"，且基线必须在**动工前**测好。
3. **灾难恢复细节**：只有 `07` §8 的"索引重建 <2h；RPO ≤5min"。缺 PG 备份策略（全量/增量/WAL 归档频率）、主从切换与回切流程、跨 AZ 副本、备份加密与勒索防护、**恢复演练频率与责任人**。元数据真相源丢失等于平台信任崩塌，而 `08` §7.4 只把"全量快照"当作一种出口格式。
4. **大客户合规细节**：`12` Q7 把等保/行业监管留给"待拍板"，`18` §2 给了 L1–L4 模板，但未回答：等保三级对日志留存与审计的具体要求、金融分级落地口径、个保法下的数据出境评估（尤其 `13` §4 的"外部 LLM 调用"与 `research/05` 提示的"GSP 把 SQL 上传云端"）、审计日志防篡改的**技术实现**（`10` §4 提到"哈希链"，但日志存哪、谁能删、如何对齐"审计日志 ≥1 年"未定义）。
5. **团队怎么招、怎么留**：`00` §10.7 把"长期 owner 与团队编制"列为待拍板第 7 条，但全文无岗位画像、技能清单（sqlglot 血缘、Trino AccessControl、越权测试、PG 调优是四类不同的人）、关键人依赖缓解方案。`00` §8 把"核心人员流失"列为风险，应对却是"诚实转为二开"——等于承认这 18 个月可能白投。
6. **治理接盘的人力从哪出**：`18` §8 要求"每域指定 Data Steward 并给工时配额"（每周 4 小时），但无测算：N 个域需多少工时、从谁的 KPI 里扣、谁负责培训。**这是"上线后无人使用"的前置原因。**
7. **血缘"待确认队列"会被淹没**：`09` §9.2 设计了"低置信/解析失败 → 待确认血缘队列 → 域负责人确认"。以 220 万实体、千万级边规模，该队列周增量可能达数千条，而**日均增量与关闭工时无人估算**，也无批量确认/超期降级设计。结果：待办中心变噪音，平台被贴上"又一个给我派活的东西"。
8. **内部竞品与回切验证**：`16` §4.2 的共存策略假设既有平台是 OM/DataHub，但真实企业更常见的是**内部自研的半成品目录**——"如何让既有团队交出所有权"全文未答，而这恰是最常见的失败原因。同时 `08` §7.4、`16` §4.3 把"可导出 = 可回切"当卖点却无验证计划；**建议把"导出后能在 OM/DataHub 成功导入并对账一致"列为 Phase 1 验收项**。

## 五、对"自研"这一根本决策的最强反驳

方案在 `12` §2 决策树与 `17` §5 七条反驳上的诚实度**显著高于一般企业方案**——尤其 `12` §4.1 主动把 Elementary 立为"必须承认的直接竞品"，并把自研理由收敛为 D7+D8。但以下反驳尚未被充分回应：

**反驳**：方案自己承认，在 5–9 个月（Phase 2）之前，它在"目录 + 质量"上赢不了"Elementary + OpenMetadata 组合"，而唯一的差异化（策略下发）要等到 **9–14 个月**。**决策层实际是在为一个 14 个月后才能验证的假设，支付 18 个月的人力成本**；这 14 个月里，团队产出的是一个"更贵的 OM"。

更关键的是：**"策略编译下发"并不像字面那样是无人区。** `research/05` §(引擎) 明确记载 Trino 提供 `SystemAccessControl` + `getRowFilter()/getColumnMask()`，结论是"写自己的 Plugin/AccessControl，**不要 fork**"；Apache Ranger 被描述为"开源世界唯一成熟的『数据级行/列策略 + 标签策略』模型，也是唯一原生输出『脱敏指令』而非布尔决策的东西"；Lake Formation / Snowflake RAP / BigQuery policy tags 均已存在（`09` §9.7 表）。**方案真正独有的其实不是"编译下发"，而是"策略的建模、申请、审批、到期回收、覆盖率度量"这一套生命周期管理**——这个定位更准确也更值钱，但方案把它写成了"编译下发"，于是留下"为什么不能用一个 Trino 插件 + 现成策略引擎做到"这个追问，且没有正面回答。

`09` §9.7 结尾把"直连 JDBC 绕过执行点"称为"必须写进产品说明的最大漏洞"，这是极优秀的诚实。但诚实到此必须再推一步：**若策略覆盖率永远到不了 100%，"数据面策略执行"作为立项理由的强度就要打折**——它挡得住走 Trino/Spark 的路径，挡不住直连。

**是否已充分回应？** 部分回应，未充分。四个缺口：① 无量化对比（三条路线 × 5 年成本 × 到首次价值时间 × 差异化可达性），只有定性叙述；② 未论证"为什么这套策略生命周期不能用更轻形态实现"（Trino 插件 + Ranger/OPA 作 PDP + 现有目录的策略对象扩展）；③ 未直面人力机会成本——`17` §5 反驳三承认"失败原因是组织而非软件"，而组织变革最需要资深数据工程师推动，自研却把这批人锁在代码里 18 个月；④ 未定义**最小区分度**（什么情况下策略下发提前到 Phase 1，什么情况下应承认二开）。

**建议**：把 `12` 第一部分的定性对照表升级为可计算的 5 年 TCO / 价值对照表，并明确"自研必须比二开多赢下哪 3 件事才值得"。做不出来，就不该开工。

## 六、最值得保留的三点（+1）

1. **血缘可信度显性化（`07` §3.2、`08` §4.4、`09` §9.2、ADR-004）**。把 `source`/`confidence`/`first_seen`/`last_seen`/`parseLevel`/`dependencyKind`/`cardinality`/`state` 全部建模到边上，并规定"`parseLevel=failed` 的边不进图，只进补全队列"。这是对"血缘不准且用户无法判断"这一真实痛点最精准的一击，也是全案唯一"别人都没做好"的原创设计。ADR-004 写"复审触发：无（长期原则）"是正确的。
2. **"绝不覆盖人工内容" + 采集变更集可整体回滚（ADR-005、`09` §9.1、`08` §5）**。字段级来源优先级（MANUAL > IMPORTED > AUTO）+ 命名空间隔离防误删 + 异常变更比例自动挂起 + `runId` 级一键回滚。三条都来自真实客户投诉，是最能建立信任、也最容易在赶进度时被砍掉的细节。
3. **能力与资源匹配的诚实框架：Spike 前置 + 退出条件 + 三档降级（`15` 全文、`00` §8、`11` §5、`17` §4）**。把 S1/S2/S3 设为 Go/No-Go 硬门槛、提前写好"周活 <20% 即停新功能""抽查正确率 <70% 即收敛范围"，并在 `12` §4 列出应放弃自研的 6 种情况。**一份方案愿意写下自己该在什么时候停止，比它承诺的功能清单更有说服力。**

**+1（同样不该砍）**：**控制面/数据面分离 + 开放标准出口（`07` §4、`08` §7.4、ADR-011）**。"平台自身不存储、不中转业务数据"加上"可导出 = 可回切"，同时解决合规与锁定焦虑。唯一要改的是把出口承诺从 7 类收窄到 2 类——因为出口即对外契约。

## 七、给决策者的三句话

1. **方案的设计质量远高于它的商业论证**：模型、血缘可信度、采集不覆盖人工内容、退出条件这几块是真功夫；但"钱从哪来、谁运维、18 个月后拿什么证明 ROI"全文没有答案——**先补 TCO 与 ROI 基线，再谈开工**。
2. **三个 Blocker 必须在上线前修掉**：图存储规模与自报 SLO 互相矛盾（`07` §3.2 vs §8 vs `11` Phase 3）、Phase 1 的 15 个连接器与 2–3 人/3 个月不自洽、MVP 故事承诺了它明确不做的数据访问生效。
3. **最强反驳没有被打败**：方案自己承认前 9–14 个月赢不了"Elementary + OpenMetadata"，而唯一差异化（策略生命周期治理）在 `07` §2 里却排在 P2。**要么把差异化提前、要么承认这是二开项目。**
