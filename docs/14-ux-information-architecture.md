# 14 · 产品信息架构与交互设计

> 状态：Draft v0.1
> 治理平台的成败常常不在后端能力，而在**信息架构**：如果用户找不到、看不懂、不想点，后端再强也没人用。这份文档定义"现代化"具体指什么。

---

## 1. 现代 vs 传统数据治理产品的 UX 差异

| 维度 | 传统（多数 2015 年代产品） | 现代化（本方案） |
|---|---|---|
| 入口 | 登录门户 → 层层点导航 → 找资产 | **搜索优先**（⌘K 全局命令面板，任意页面可搜）；信息出现在用户已有的工作现场（IM / CI / BI / IDE） |
| 组织方式 | 按技术分层（数据库→表） | 按**用户意图**组织：找人、找口径、找血缘、找待办、找质量；技术层级是筛选维度而非导航主干 |
| 元数据呈现 | 属性表格堆砌，几百个字段平铺 | **渐进披露**：概览（做什么用）→ 关键属性 → 全部属性；每块信息都回答一个问题 |
| 血缘 | 静态大图，看不出可信度与时间 | 交互式探索 + **边按来源/置信度/时效区分线型** + 聚焦/路径高亮 + 时间轴回放 |
| 变更 | 只有当前状态 | **Diff 优先**：默认展示"相比上周变了什么"（很多人只用这个功能） |
| 治理动作 | 阅读型报表、"覆盖率 47%" | **可执行待办**：每个指标都能点进去、分配到人、关闭、留痕 |
| AI | 悬浮聊天窗 | 嵌入具体工作流：描述生成（编辑器内联）、影响摘要（PR 内）、问答（带引用） |
| 语言 | 英文 + 技术黑话 | 中英双语 + 术语表驱动的"业务语言"（搜"成交额"能命中 GMV） |
| 权限可见性 | 无感，遇到 403 才知 | 资产卡片显示可见性状态与申请入口 |

## 2. 全局导航（六个一级入口）

```
┌────────────────────────────────────────────────────────────────┐
│  🔍 全局搜索（⌘K）        域切换 ▾   🔔 通知   👤 我            │
├────────────────────────────────────────────────────────────────┤
│  发现 │ 资产 │ 血缘 │ 质量 │ 治理 │ 管理                        │
└────────────────────────────────────────────────────────────────┘
```

| 一级入口 | 内容 | 主要用户 |
|---|---|---|
| **发现 Discovery** | 搜索主页、热门/趋势资产、按域浏览、术语表入口、数据产品货架 | 所有数据用户 |
| **资产 Assets** | 我的资产（我拥有/我关注/我常看的）、资产详情（统一页）、收藏与集合 | 数据用户 + Owner |
| **血缘 Lineage** | 血缘探索器、影响分析、血缘健康（未确认血缘队列） | 分析师、工程师、Owner |
| **质量 Quality** | 剖析概览、质量规则与结果、SLO 与事故、告警订阅 | 数据工程师、治理团队 |
| **治理 Governance** | **待办中心（Action Center）**、术语表管理、分类分级复核、契约管理、访问申请审批、健康分与记分卡 | 治理团队、数据管家、Owner |
| **管理 Admin** | 平台与连接、采集任务与运行、模型扩展、权限与策略、审计日志、系统设置 | 平台管理员 |

**关键设计**：`待办中心` 是给"治理执行者"的首页默认页——治理平台必须有"今天我要做什么"的视图，而不是只有"数据全景"。

## 3. 关键页面设计（文字线框）

### 3.1 全局搜索（⌘K 命令面板 + 搜索页）
```
┌ ⌘K ────────────────────────────────────────────────────────────┐
│ [ 订单 客户 ]                                        ⏎ 全部结果  │
├────────────────────────────────────────────────────────────────┤
│ ▸ 直接跳转   订单明细表 dw.orders_detail          ⭐ 常用        │
│ ▸ 资产 (23)  订单宽表 · 订单维表 · 订单明细 ...                  │
│ ▸ 术语 (2)   订单金额口径 · 有效订单定义                         │
│ ▸ 列 (48)    order_id · customer_id · order_status              │
│ ▸ 文档/契约  订单域数据契约 v2.1                                 │
│ ─────────────────────────────────────────────────────────────── │
│ 快捷：查看血缘 │ 申请访问 │ 找 Owner │ 提工单                    │
└────────────────────────────────────────────────────────────────┘
```
要点：**命令面板同时是"动作入口"**（不只是搜索），支持 `lineage <资产>` 这类命令；结果分组并显示命中原因（为什么它相关）。

### 3.2 资产详情页（统一模板，所有资产类型共用）
```
┌ 面包屑：发现 › 订单域 › dw.orders_detail          ⭐关注  ⋯更多  │
│ 表名 + 平台徽标 + 健康分徽标(82 良) + 分级徽标(L2 内部)          │
│ 一句话描述（AI 草稿标记 ✨ / 人工 ✓）                            │
├──────────────┬─────────────────────────────────────────────────┤
│ 概览 Overview │ Owner: @张三(技术) @订单组(业务)   [联系/申请]    │
│ Schema       │ 数据量: 2.3 亿行 · 日增 300 万 · 更新于 2h 前     │
│ 血缘 Lineage │ 质量: ✅ 12/13 通过  ⚠ 1 条告警                  │
│ 质量 Quality │ 契约: v2.1 (兼容)  SLO: 达成 99.7%               │
│ 契约 Contract│ 使用: 42 人/月 · 1280 次查询 · 被 6 个报表引用   │
│ 使用 Usage   │ 关联术语: 订单金额口径 · 有效订单                  │
│ 讨论 Discuss │ ─────────────────────────────────────────────── │
│ 变更 History │ [ 预览数据 ]  [ 复制查询 ]  [ 申请访问 ]  [ 编辑 ]│
└──────────────┴─────────────────────────────────────────────────┘
```
规则：
- **首屏只回答四个问题**：这是什么、谁负责、能不能用、数据好不好。
- 每个"治理缺口"就地可操作（无 Owner → "认领"；无描述 → "✨生成"；无分级 → "标注"）。
- 变更页默认展示 diff（schema / 契约 / 质量 / 血缘），而不是流水账。

### 3.3 血缘探索器
```
┌ 焦点: dw.orders_detail.customer_id     方向: ⇅  深度: 3  过滤: 表级▾ 置信度≥0.7▾ │
├──────────────────────────────────────────────────────────────────────────────┤
│   [ods_orders]───▶[stg_orders]───▶[dw.orders_detail]───▶[rpt_gmv_daily]       │
│        │                                ╎(虚线=解析)          │               │
│        └──▶[ods_customer]──▶[dim_customer]┘                   └──▶[看板:GMV]   │
├──────────────────────────────────────────────────────────────────────────────┤
│ 选中边: ods→stg  customer_id  IDENTITY  来源: SQL解析 置信 0.82  近30天未见更新│
│         [ 查看 SQL ] [ 确认此血缘 ] [ 标记为错误 ]                             │
└──────────────────────────────────────────────────────────────────────────────┘
```
要点：**线型 = 可信度**（实线运行时/人工、虚线解析、点线推断、灰线过期）；每条边可确认/驳回（喂养置信度模型）；支持时间轴（"三个月前的血缘"）。

### 3.4 影响分析（变更前的决策界面）
```
变更：删除列 dw.orders_detail.amount  →  影响 17 个资产 / 8 位负责人
┌ 🔴 阻断级 (2)  对外报表 GMV 看板、风控特征表

│ 🟡 提示级 (10) 仅表级依赖

```

### 3.5 待办中心（治理执行者的工作台）
```
我的待办 (34)   [ 分配给我 | 我的域 | 全部 ]
┌ 类型          对象                  建议动作        优先级  SLA    ┐
│ 分类复核      dw.user_profile        确认 PII 分级   🔴 高   2天   │
│ 血缘确认      ods→stg 12 条边        批量确认        🟠 中   7天   │
│ 缺 Owner      ods_temp_2024          指派负责人      🟠 中   7天   │
│ 契约违约      orders_detail          处理 schema 变更 🟠 中  3天   │
│ 访问审批      风控组申请 3 列         审批             🔴 高   1天   │
└ 共 34 项，预计 45 分钟                       [ 批量操作 ] [ 规则自动化 ] ┘
```
要点：**"预计耗时"与批量操作**是提升关闭率的关键设计；高频人工动作应能转为自动化规则（"此类待办自动完成/自动跳过"）。

## 4. 交互原则（可执行的 UX 约束）

| 原则 | 具体约束 |
|---|---|
| **3 秒法则** | 任意资产详情页首屏 3 秒内回答"这是什么/谁负责/能用吗/数据好吗" |
| **零死胡同** | 每个空状态都给出下一步动作（无描述 → 生成；无 Owner → 认领；无权限 → 申请）；绝不出现"暂无数据"就结束 |
| **可解释的分数** | 健康分、质量分、相关性排序都必须能点开看构成与扣分原因 |
| **来源可见** | 每条元数据标注来源（人工/AI/采集/导入）与更新时间，AI 内容用 ✨ 区分 |
| **不打断** | 通知聚合与限频；批量操作提供撤销；破坏性操作二次确认 + 影响面预览 |
| **无障碍与国际化** | 键盘可达（搜索、血缘探索、审批流全程可键盘操作）、对比度达标、中英双语 + 术语可翻译 |
| **性能即体验** | 首屏 < 1.5s、搜索 < 500ms、图交互 60fps（>2000 节点切换聚合视图）；骨架屏而非转圈 |
| **移动/嵌入可用** | 关键动作（搜索、查看、审批、告警）在移动端与 IM 内可完成 |

## 5. 交付形态的设计一致性

| 形态 | 设计要点 |
|---|---|
| Web 应用 | 主力界面；上述全部页面 |
| 嵌入式 Widget | 只读精简卡：资产摘要 + 健康分 + 血缘入口 + 申请入口（用于 BI/IDE/数据平台内嵌） |
| IM 机器人 | 搜索、订阅、告警、审批（按钮式）、待办提醒 |
| CLI (`dgctl`) | 与 API 一致：`search` / `get` / `lineage` / `apply -f`（治理即代码）/ `diff` / `doctor` |
| IDE / CI 插件 | 当前文件对应的表血缘、契约校验结果、影响面评论 |
| 浏览器扩展（可选） | 在任意网页中选中表名 → 侧栏展示治理信息（低成本的"到现场去"） |

## 6. 设计系统与前端工程约束

- 基于成熟组件库（Ant Design 5 或 shadcn/ui + Radix），**不自研基础组件**；自研的是资产页模板、血缘画布、Diff 视图、待办中心四类"业务组件"。
- 状态管理：TanStack Query（服务端状态）+ 少量本地状态；避免自建全局 store 复制服务端数据。
- 图谱渲染：Cytoscape.js / AntV G6（WebGL），统一封装为 `<LineageGraph>` 业务组件（布局、过滤、聚焦、时间轴能力内聚）。
- 表格：虚拟滚动（列数 > 100 的表结构、> 1000 行的搜索结果）。
- 主题：支持企业品牌色（客户部署常见需求）；暗色模式（工程师偏好）。
- 埋点：所有关键动作（搜索→点击、血缘展开、待办关闭、建议采纳）埋点，作为采纳度 KPI 与 UX 优化的数据来源。
