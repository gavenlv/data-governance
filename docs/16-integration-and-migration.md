# 16 · 集成地图与迁移评估

> 状态：Draft v0.1
> 定位：治理平台从来不是孤岛。**它的价值取决于它能接进多少现有系统、被多少现有流程调用。** 本文给出集成清单、对接方式与失败降级策略，以及从既有平台迁移的评估口径。

---

## 1. 集成设计原则

1. **双向优于单向**：不仅从周边系统采集，还要把治理结论**推回**周边系统（否则用户永远不打开治理平台）。
2. **降级不阻断**：任何集成失败都不得阻断业务主流程（例如 CI 插件不可用时降级为"跳过 + 记录"，而非让流水线挂死）。
3. **标准协议优先**：能用 OpenLineage / OIDC / SCIM / OCSF / Webhook 就用标准，减少定制适配。
4. **幂等与可重放**：所有入站数据带外部唯一 ID 与幂等键。
5. **权限一致**：入站认证、出站授权都走同一套模型，禁止"集成专用的超级权限"。

## 2. 集成地图

```
                        ┌─────────────────────────────┐
        采集（入）        │      数据治理平台            │        推送（出）
   ┌────────────────────┤                             ├────────────────────┐
   │ 数据库/数仓/湖仓     │  L1 接入  L2 派生  L3 核心   │  CI/CD（门禁与评论） │
   │ BI 工具              │  L4 能力  L5 体验            │  IM（告警/审批/订阅）│
   │ 调度与 ETL           │                             │  工单（Jira/禅道）   │
   │ 消息与 Schema Registry│                            │  查询引擎（策略下发） │
   │ 外部 Catalog（联邦）  │                             │  BI（可见性下发）    │
   │ 身份源（SSO/SCIM）    │                             │  IDE/编辑器（插件）  │
   │ 代码仓库（dbt/SQL）   │                             │  AI Agent（MCP）     │
   └────────────────────┴─────────────────────────────┴────────────────────┘
```

## 3. 逐类集成规范

| # | 周边系统 | 方向 | 方式 | 频率 | 失败降级 |
|---|---|---|---|---|---|
| I1 | 数据库/数仓 | 入 | JDBC + `information_schema` / 原生元数据 API | 日/小时 | 保留上次快照，标记 `stale`；告警 |
| I2 | Hive Metastore | 入 | Thrift API（直连或经代理） | 小时 | 降级为 JDBC 采集 |
| I3 | 湖仓表格式（Iceberg/Delta/Hudi） | 入 | Iceberg REST Catalog / HMS / Glue API | 小时 | 只采 Catalog 层元数据 |
| I4 | 调度/ETL（Airflow、DolphinScheduler、Dagster） | 入 + 出 | 入：读 DAG/任务定义 + 接收 OpenLineage；出：推送"待治理任务"到 DAG 的 CI | 任务级/实时 | 纯静态解析作业定义 |
| I5 | dbt | 入 | `manifest.json` + `catalog.json` + `run_results.json`（CI 产物或 dbt Cloud API） | 每次运行 | 读取仓库中的 dbt 项目文件 |
| I6 | Spark / Flink | 入 | OpenLineage listener / 作业提交时上报 | 实时 | 静态解析作业 SQL |
| I7 | Kafka / Schema Registry | 入 | Admin API + SR REST | 小时 | 仅采集 Topic 列表 |
| I8 | BI（Superset/Tableau/PowerBI/Metabase） | 入 + 出 | 入：REST API 拉报表与字段映射；出：下发可见性/字段隐藏 | 日/事件 | 只读目录，不下发策略 |
| I9 | 查询引擎（Trino/Spark/Doris/StarRocks） | 入 + 出 | 入：`system.query_log` 等；出：**策略下发**（行过滤/列掩码） | 事件 + 定时对账 | 保留上一条生效策略，告警并阻断新策略发布 |
| I10 | 身份源（AD/LDAP/OIDC/SCIM） | 入 | OIDC 登录 + SCIM 同步用户与组织 | 实时/日 | 缓存上次同步结果，只读模式 |
| I11 | IM（钉钉/飞书/Slack/Teams） | 出 + 入 | 出：告警/订阅/摘要；入：审批按钮回调、搜索指令 | 事件 | 降级为邮件/站内信 |
| I12 | 工单（Jira/禅道/ServiceNow） | 出 + 入 | 出：创建治理任务/事故；入：状态回写 | 事件 | 站内待办兜底 |
| I13 | CI/CD（GitHub/GitLab/Jenkins/Argo） | 出 + 入 | 出：PR 评论 + check status；入：仓库中的契约/策略文件 | PR 事件 | **降级为不阻断 + 记录**（绝不挂死流水线） |
| I14 | 代码仓库（治理即代码） | 入 + 出 | 入：`dg/` 目录下的契约/策略/术语/质量规则；出：平台变更自动提 PR（可选） | PR 事件 | 手动 apply |
| I15 | 对象存储（S3/OSS/MinIO） | 入 | 桶/前缀元数据 + Parquet schema 推断 | 日 | 仅路径清单 |
| I16 | ML 平台（MLflow/Kubeflow/特征库） | 入 | 各自 REST API | 日 | 跳过 |
| I17 | 外部 Catalog 联邦（Glue/Unity/Polaris/Gravitino） | 入（只读） | 各自 API；外部为权威时平台侧 `readOnly` | 小时 | 本地缓存 |
| I18 | AI Agent / 外部助手 | 出 | MCP Server（以调用者身份鉴权） | 实时 | 无 |
| I19 | 内部门户/搜索 | 出 | 嵌入式 Widget / API | 实时 | 无 |
| I20 | 可观测性平台 | 出 | OpenTelemetry（平台自身） | 持续 | 无 |

### 三个"必须有"的集成（MVP 就要）
1. **I13 CI 插件**：治理进不了 CI 就不会持续；
2. **I11 IM**：不进 IM 的通知等于没通知；
3. **I9 查询引擎（入）**：查询日志是"行为元数据"与血缘的主要来源（成本最低、覆盖最广）。

## 4. 迁移与共存评估

### 4.1 迁移来源与工作量评估口径

| 来源 | 可迁移内容 | 迁移方式 | 主要难点 |
|---|---|---|---|
| **OpenMetadata** | 实体、Aspect、血缘、术语、标签、Owner | 官方 REST API 全量导出 → 转换器 → 平台导入 | 概念映射（Service/IngestionPipeline/Persona 无对应物）；血缘的来源/置信度信息缺失（需回填为 `source=imported`） |
| **DataHub** | 实体、Aspect、血缘、Domain、Glossary、Policy | GraphQL/OpenAPI 滚动导出（`scrollAcrossEntities`） | Aspect 与自研模型的字段映射；URN 体系转换需保留 `externalRefs` 以便回切 |
| **Apache Atlas** | 实体、分类、血缘 | Atlas API 全量导出 | TypeSystem 与统一模型差异大；分类传播历史难迁移 |
| **商业产品**（Collibra/Alation 等） | 资产、术语、分级、Owner、部分血缘 | 通常只能经 API/导出报表 | 导出能力与配额限制；血缘与策略往往无法导出（**这是锁定风险的实际体现**） |
| **Excel/Confluence/人工维护的清单** | 术语表、Owner、分级 | 模板导入 + 校验 | 数据质量差、需要去重与冲突解决流程 |

**迁移工具应作为产品的一部分**（`dgctl import --from openmetadata`），而不是一次性脚本——因为客户环境里这类迁移会反复发生（也便于未来"回切"以降低锁定风险，这本身就是卖点）。

### 4.2 共存策略（不建议"一刀切替换"）
| 阶段 | 策略 |
|---|---|
| 0 只读集成 | 平台作为"第二目录"，从既有平台/系统拉取，先证明价值（不要求任何人改变习惯） |
| 1 增量治理 | 新资产在新平台治理；旧资产按需回填；两边通过 ID 映射保持引用 |
| 2 单一入口 | 用户在旧平台的入口加跳转/嵌入（把新平台作为能力提供者） |
| 3 收敛 | 旧平台只读归档；平台成为唯一治理入口（**必须有明确的时间点与负责人，否则会永久双跑**） |

### 4.3 迁移风险清单
| 风险 | 应对 |
|---|---|
| 迁移后血缘断裂 | 保留 `externalRefs` 与别名表；迁移前后做血缘数量对账 |
| 人工成果丢失 | 迁移前后做资产健康分对账，抽查人工描述/标签是否完整 |
| 迁移期双写不一致 | 迁移期设"单一写入方"（一个平台只写不读，另一个只读），禁止双写 |
| 回切成本 | 保留幂等导出能力（**可导出 = 可回切**，降低锁定风险，也让决策层更放心自研） |
| 迁移窗口过长 | 分域迁移（一个域迁完再迁下一个），每域有验收标准 |

## 5. 集成质量的可观测性

每个集成都要被度量，否则"接入失败"会静默很久：
- 每个连接的**最近成功时间**、**连续失败次数**、**延迟分布**；
- 入站数据的**新鲜度**（最后一条外部事件时间）与**量级异常**（骤降/骤增告警）；
- 出站推送的**成功率与重试队列积压**；
- 统一的"集成健康"页面（管理员首页），并有"诊断包导出"（脱敏）用于支持排查。

**这一条是很多开源平台的真实缺口**：连接配了以后就没有健康视图，等到用户发现"目录半年没更新"时已经没人信任它了。
