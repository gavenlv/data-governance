## 1. 方法与口径

- **对比对象**：开源（OpenMetadata、DataHub、Apache Atlas、Amundsen、Marquez、Gravitino 等）+ 商业（Collibra、Alation、Informatica、Atlan、Microsoft Purview、Google Dataplex/Knowledge Catalog、AWS Glue/DataZone、Select Star、Datafold、Monte Carlo/Bigeye、dbt/Cube）+ 国内（DataWorks/Dataphin、DataLeap、WeData、星环、袋鼠云、华为 DataArts）。
- **评分口径**：● 强（开箱即用且成熟）／◐ 中（有但需较多配置或较浅）／○ 弱（能力有限或需大量自研）／— 无（不具备）。
- **时效与免责**：以 **2026 年 10 月**为基准。商业产品能力随版本快速变化，评分为"设计中位水平"判断；易变事实（版本、定价、连接器数量）以 `research/03` 的标注与官方文档为准。

### 1.1 必须先知道的七项市场变化（2024–2026，详见 `research/03` §1）

这些变化直接影响"自研 vs 采购"的判断：

| 变化 | 事实 | 对我们的含义 |
|---|---|---|
| **商业厂商被大厂吞并** | Informatica 于 2025-11-18 被 Salesforce 以约 80 亿美元收购完成并从 NYSE 退市；Select Star 于 2025-11 被 Snowflake 收购并入 Horizon Catalog | **"买目录"= 长期绑定单一云厂商战略**从理论风险变成既成事实 → 自研的"可控性"论点显著增强 |
| **治理赛道在向"访问治理/策略执行"集中** | Collibra 2025-06 收购 Raito（数据访问治理）；Alation 2025-05 收购 Numbers Station（AI Agent 能力） | 商业巨头用并购补齐的正是**策略执行与 AI** 两块 → 印证我们选定的差异化方向 |
| **开源阵营进入"目录层被标准化接管"阶段** | Apache Gravitino 于 2025-09 发布 1.0.0 并毕业为 ASF 顶级项目；Apache Polaris 于 2026-02 毕业为 TLP；Iceberg REST 成为事实标准 | **元数据联邦层可以直接复用 Gravitino**，不必自研"接一堆异构 Catalog"的脏活 |
| **Hadoop 时代项目批量退场** | Apache Griffin 于 2025-11 退役进 Attic；Amundsen 于 2026-09 被 GitHub 归档；WhereHows/Metacat 实质停更；Atlas 发布节奏降至约两年一个 minor | 不要再参考这些项目的架构决策（除失败教训）；也说明**这个领域的项目寿命很短，架构上必须保证"可迁移、可导出"** |
| **契约与语义层被标准化** | ODCS 发布 v3.2.0（2026-09）；`datacontract` CLI 支持 lint/test/export/breaking 与 25+ 格式导出；语义层标准 OSI 捐给 ASF 成为 Apache Ossie (Incubating) | **契约与语义层不自造**：直接对齐 ODCS + CLI 生态，平台的增量在"接入治理闭环与策略" |
| **MCP 成为 Agent 接入元数据的事实标准** | **MCP 2026-07-28 已是正式规范（不是 RC）**，核心变化是**无状态化（移除 session）**；**2025-12-09 已随 Agentic AI Foundation（AAIF）捐赠给 Linux Foundation**——**"Anthropic 的 MCP"这一表述已过时**；OpenFGA 于 2025-11 成为 CNCF 孵化项目 | ① AI 出口走 MCP；② **工具级授权必须从第一天设计进授权层**（事后补几乎必然重构）；③ **无状态化意味着身份/权限/审计必须逐请求显式传递**，不能再依赖会话隐式承载；④ 规范演进走 SEP 流程——**这是治理平台提出"目录/血缘语义"协议扩展的正规入口** |
| **开源龙头集体转向"AI 上下文层"** | OpenMetadata 自 2.0（2026-02）起自我定位为 **"The Open Context Layer for AI Agents"**；Collate 于 2026-02-24 发布 **Semantic Intelligence Graph**（企业 AI Agent 的持久语义记忆层）；DataHub 提供官方 `mcp-server-datahub` | **印证了 `13` 的方向**（语义层一等公民 + MCP 出口 + 元数据作为 Agent 上下文）；同时意味着一件事：**"只做元数据目录"的定位正在贬值**——元数据必须绑定下游消费（BI / CI / 查询引擎 / Agent）才有价值，这正是本方案"元数据是产品而非文档"立场的外部验证 |

## 2. 开源双雄：OpenMetadata vs DataHub（最值得研究的两个）

### 2.1 能力对比

| 维度 | OpenMetadata | DataHub | 结论 |
|---|---|---|---|
| 模型 | 单一 JSON-Schema 驱动实体模型；FQN 层级；关系表承载血缘 | Entity + Aspect + URN；PDL 定义 + 代码生成 | 两者都值得抄：**OM 的"单一 Schema 即事实源"**（根治 API/SDK/UI 不一致）+ **DataHub 的 Aspect 粒度**（多方部分更新） |
| 变更传播 | API 写库 + 索引刷新 + ChangeEvent | Kafka MCE/MAE/MCL 事件流，生态以消费者扩展 | 抄 DataHub 的事件驱动思想，**但去掉 Kafka 硬依赖与多存储平级双写** |
| 存储 | RDBMS + 搜索引擎（**不上图数据库**） | RDBMS + ES + 可选图库（运维重） | 抄 OM 的组件精简；图能力按需作派生视图 |
| 血缘 | sqllineage/dbt/BI/查询日志 + 手工；列级开箱即用 | sqlglot 列级 + OpenLineage + BI 集成，**跨平台聚合更强** | 抄 DataHub 的"多源汇聚实用主义"；补上我们要做的**置信度与来源显性化**（两者都没做好） |
| 采集 | Python 独立进程、多类 Workflow（metadata/usage/lineage/profiler/classification/…）、YAML+JSON Schema 校验 | Python recipe（source→transformer→sink）、Stateful Ingestion、连接器生态最广 | **两者都抄**：OM 的 Workflow 分层 + DataHub 的声明式 recipe 与 transformer 组合 |
| 数据质量 | 内置 profiler + 测试 + 数据契约（OSS 较完整） | Assertions/Contract（云版更强） | 抄 OM 的"OSS 即完整"；质量执行与血缘、契约的联动要做更深 |
| 治理/协作 | Feed + Task + Announcement + Workflow（治理闭环较早入 OSS） | 有 Domain/Data Product/Glossary，协作偏轻 | 抄 OM 的协作闭环（**"把人纳入流程"是提升覆盖率的关键**） |
| 扩展 | 自定义属性、自定义连接器/测试、Application 插件；改 Schema 属重扩展 | PDL 自定义模型（能力最强，但需 Java + 重部署） | 自研时取中间路线：**YAML 模型注册表 + 热加载 + 代码生成**（比 OM 强，比 DataHub 轻） |
| 权限 | RBAC/Policy/Persona（平台内） | Policy 四元组（Actors/Privileges/Resources/Conditions）（平台内） | **都不下发数据面**——这是我们要做的差异化 |
| 运维复杂度 | 中（RDBMS + ES） | 高（Kafka + ES + RDBMS + 可选图库 + upgrade Job） | 目标：**单机 compose 一条命令起，生产只加 Kafka** |
| 升级 | 月更 + 破坏性变更 + 采集端与服务端版本必须对齐 | 每版本 DB 迁移 + 索引重建；摄取框架跨版本破坏性变更 | 我们要把"**模型兼容性**"作为独立承诺并做 CI 强制 |

### 2.2 两者共同的结构性短板（我们的机会）
1. **血缘不可信**：多来源汇入后不区分可靠性，解析失败还静默返回空 → 用户整体不信任血缘。
2. **治理停在元数据层**：权限只管"能不能看资产卡片"，不管"能不能读数据行/列"。
3. **AI 粗放**：要么没有，要么直接把 LLM 输出写进元数据，缺 provenance 与人工确认。
4. **运营闭环弱**：KPI 报表有，"可分配到人并关闭的待办"弱（OM 有 Task，但不够）。
5. **企业网络现实**：以服务端拉取为主，私有子网/数据不出域场景吃力。

## 3. 商业厂商：各自真正的杀手锏（我们该抄的）

> 商业产品的价值不在"功能条目多"，而在**某个环节的深度**。逐家提炼"最值得抄的一个设计"。

| 厂商 | 最值得借鉴的一个设计 | 为什么强 | 我们怎么落地 |
|---|---|---|---|
| **Collibra** | **Operating Model + 可配置工作流引擎**：把"谁对什么资产负什么责任、走什么流程"建模成一等公民，配审批、分派、SLA | 治理本质是组织流程；商业产品赢在"能把流程固化并度量" | 自研轻量状态机 + Action Center（待办即流程实例），审批链带 SLA 与超时升级 |
| **Alation** | **查询日志驱动的行为元数据**（Behavioral Analysis）：用真实使用数据算人气、推荐、以及"高价值但无人治理"的资产 | 让治理优先级由**真实使用**决定，而非拍脑袋；显著提升搜索相关性 | 查询日志挖掘管道 + 热度/趋势/共现推荐 + "高频访问但无 Owner/无文档"自动生成治理待办 |
| **Informatica** | **元数据驱动的 AI 推荐引擎（CLAIRE 式）**：在采集/映射/质量/主数据多个环节用元数据做自动推荐与加速 | 把 AI 用在"降人力"上，而不是做聊天窗 | AI 建议引擎（描述/标签/术语映射/规则推荐）+ 采纳率闭环（见 `13`） |
| **Atlan** | **现代协作式 UX + 资产 360**：信息密度与美观兼顾，把治理信息嵌入日常协作（评论、@、收藏、集合） | 决定采纳率的是 UX，不是后端能力 | `14` 的信息架构：搜索优先、渐进披露、每个缺口就地可操作 |
| **Microsoft Purview** | **扫描器 + 分类器 + 敏感信息标签 + 与合规体系打通**（含数据地图、血缘、DLP 联动） | 合规是企业刚需，且必须"有证据" | 分类分级（列级传播）+ 合规框架映射 + 审计报告一键导出 + 与策略执行联动 |
| **Google Dataplex / AWS DataZone** | **Data Product / 数据订阅的市场化抽象 + 与云原生存储计算深度集成** | 把"数据共享与订阅"产品化，治理与云原生权限体系合一 | Data Product 一等公民 + 货架式发现 + 访问申请与云原生策略映射 |
| **Monte Carlo / Bigeye（可观测性）** | **血缘驱动的影响面 + 置信度/严重度分级 + 事故管理闭环**；告警带"影响哪些下游、多少用户" | 可观测性产品的核心是**降噪**与"告诉我该做什么" | 异常 → 聚合为 Incident → 血缘算影响面 → Timeline → Postmortem → 沉淀规则（闭环） |
| **dbt / Cube（语义层）** | **指标定义的代码化与单一事实源**（指标口径可版本化、可测试、可追溯） | 从"数据集治理"上升到"口径治理"，直接服务 AI/BI | 接入 dbt Semantic Layer/Cube 的指标元数据，把指标口径挂到物理列与血缘上 |
| **Select Star / Datafold（DevEx 侧）** | **把治理嵌进开发流程**（CI 中的 schema diff、变更影响 PR 评论、字段级 diff） | 治理只有进 CI 才可持续 | CI 插件（契约校验 + 血缘影响评论 + 治理属性必填检查） |
| **国内（DataWorks / DataLeap / WeData）** | **与调度/开发/发布一体化的治理**（数据开发 → 发布 → 质量 → 安全 → 成本 全链路内建），且**中文语境与本地合规适配** | 在国内企业里，"治理"很难脱离开发平台单独存在 | 明确 Non-Goal（不做开发调度），但**提供与调度/开发平台的双向集成插件** + 中文语义与国标分级模板 |

### 3.1 商业产品的已知硬伤（我们要避免的）

| 硬伤 | 具体表现 | 我们的对策 |
|---|---|---|
| **组件割裂、概念三套** | 云厂商体系常见：技术元数据在一个服务、权限在另一个服务、业务目录在第三个服务（如 AWS 的 Glue Catalog + Lake Formation + DataZone），用户要在脑中维护映射 | 单一元数据模型 + 单一权限模型（`08`）；云原生能力通过**适配器**对接，不分裂自身模型 |
| **血缘存在功能性上限** | 有厂商的运行时血缘在超过一定规模（如百余张表）后中断失败，属"功能阻断"而非性能问题 | 血缘以**静态解析为主干**（不依赖运行时全覆盖），运行时上报作为高置信补充（`09` §9.2） |
| **私有化能力受限** | 多数商业产品以 SaaS 多租户为主，私有化仅"区域变体"或需专门商务；自部署仅限连接器 runtime | 自研天然可私有化：Compose 单机 → Helm 生产 → 联邦版（`07` §4） |
| **成本不透明** | 多服务叠加计费（存储 + 请求 + 计算 + 目录用量），客户普遍反映"看不出总额来自哪里" | 成本内建到治理 KPI（`09` §9.8），平台自身资源消耗可观测 |
| **锁定风险** | 血缘与策略常无法完整导出，迁移等于重建 | **"可导出 = 可回切"**作为产品要求，并把迁移工具作为产品一部分（`16` §4） |
| **治理停留在门户** | 商业产品强在门户与流程，但难以嵌入客户自研的 CI/IDE/内部平台 | 开放 API/CLI/插件/嵌入组件/MCP，主动"到现场去"（`14` §5） |

## 5.「取各所长」汇总清单（本方案的能力来源）

| 能力 | 来自谁（灵感） | 我们的实现（改进点） |
|---|---|---|
| Schema 单一事实源 + 代码生成 | OpenMetadata | 模型注册表 YAML → 生成 Java/Python/TS + OpenAPI；CI 强制向后兼容 |
| Aspect 粒度建模与部分更新 | DataHub | 保留 Aspect，但**真相源唯一**（PG），图/搜索全为派生 |
| 事件驱动 + 可重放 | DataHub | 事务内 outbox → 事件流 → 消费者；**取消多存储平级双写**，UI 显示索引 watermark |
| 一切皆实体（术语/域/契约同构） | DataHub | 术语、数据产品、契约、Suggestion、Incident 都是一等实体，复用权限/搜索/通知 |
| 声明式采集（recipe + transformer + stateful） | DataHub | 采集框架：Source→Stage→Sink + 字段级来源优先级 + 变更集回滚 |
| 采集多 workflow 分层 | OpenMetadata | metadata/usage/lineage/profiler/classification/quality 六类作业独立调度与限额 |
| 治理协作闭环（Feed/Task/Announcement） | OpenMetadata | 升级为 **Action Center**：可分配、可估时、可批量、可自动化的待办中心 |
| 多源血缘汇聚 | DataHub | 增加**置信度融合 + 来源标注 + 时间衰减 + 冲突队列** |
| 列级 SQL 解析 | DataHub（sqlglot） | 直接复用 sqlglot；自建方言语料回归集；失败显式降级 |
| 血缘不用图数据库的克制 | OpenMetadata | PG 边表 + 递归 + 物化闭包；图库仅在实测需要时作派生视图 |
| 自动分类的规则+采样路线 | OpenMetadata / Purview | 规则 + 格式校验 + 统计 + 模型融合，**中低置信进复核队列** |
| **分类标签沿血缘传播** | Atlas / Informatica / Purview | 列级优先传播 + 来源区分 + 冲突取严格 + 可显式阻断（聚合/脱敏） |
| 行为元数据（使用驱动治理） | Alation / Amundsen | 查询日志挖掘 → 热度/推荐/共现 + "高价值无治理"待办 |
| Operating Model / 工作流 | Collibra | 轻量状态机 + SLA + 超时升级；不自研 BPMN |
| 元数据驱动的 AI 推荐 | Informatica（CLAIRE 式） | AI 建议引擎 + 采纳率闭环 + provenance（`13`） |
| 现代化协作 UX / 资产 360 | Atlan | `14` 的信息架构与统一资产页模板 |
| 合规标签与审计证据 | Purview | 分级可配 + 合规映射 + 审计报告导出 + DSAR 支撑（P2） |
| Data Product / 订阅市场 | DataZone / Dataplex | Domain + DataProduct 一等公民 + 货架 + 访问申请 |
| 可观测性：降噪 + 影响面 + 事故闭环 | Monte Carlo / Bigeye | 异常聚合为 Incident + 血缘影响面 + Postmortem 沉淀规则 |
| 血缘驱动的 CI diff | Datafold / Select Star | CI 插件：契约兼容 + 血缘影响 + 治理必填检查 |
| 指标口径代码化 | dbt / Cube | 接入其语义层元数据，指标可追溯到物理列 |
| 与开发/调度一体化（中文语境） | DataWorks / DataLeap | 不做开发平台，但提供调度/开发平台双向集成插件 + 中文术语体系 |
| **资产可信状态机（Trust Flags）** | Alation | 资产级"已认证 / 有警告 / 已弃用"显式状态，**展示优先级高于描述完整度**——用户最想先知道"这数据能不能信" |
| **质量结果接入契约（不自研 DQ 引擎）** | Alation | 先定义"质量结果摄入 API"（谁都能推结果进来），再考虑自研执行器；这让平台能立刻接入客户已有的 DQ/GX/dbt 投资 |
| **元数据可编程（Apps + 无代码自动化）** | Atlan | 扩展槽位 + 事件触发动作，让业务方自己配置治理规则；**长期采纳率取决于"能否自助扩展"而非功能清单长度** |
| **零数据出域** | Elementary | 计算推向客户自己的数仓，平台侧只做 UI 与协作——合规场景的杀手级特性，也让平台职责大幅变轻（与我们的"控制面/数据面分离"一致，但更彻底） |
| **血缘引擎可解耦 + 代码静态分析** | IBM Manta | 血缘不只解析 SQL：**静态代码分析覆盖 PL/SQL、存储过程、Java/C# 字节码**，且血缘引擎可独立部署、可导出给其它平台（支持 OpenLineage 摄取）。**只看 SQL 会漏掉传统数仓最重的一块** |
| **分级之后的"使用诊断"** | 阿里 DataWorks（数据保护伞） | 分级→识别→脱敏→**谁在怎么用**的闭环诊断；否则合规只停在打标 |
| **元数据/血缘的开放写入面** | 阿里 DataWorks（OpenAPI） | 血缘不能只靠自家解析，必须允许外部系统批量写入自定义实体与血缘，否则覆盖率永远是瓶颈 |
| **可扩展元数据 schema + 开放写入** | Google Knowledge Catalog（Aspect Type） | 企业可自定义 aspect 并绑定任意条目（含外部系统注入）——自研必须正面对标（我们的模型注册表 + 开放 API） |
| **审批结果自动落到真实权限** | AWS DataZone | "目录即权限入口"：审批通过后自动生成真实数据权限。这就是 `ADR-008` 策略编译下发的目标形态，**也是自研最有价值的差异化方向** |
| **策略物理执行于数据流** | Informatica（CDAM） | 访问策略不是"登记在目录里"，而是在数据管道转换中被强制施加（知识图谱跑在 Amazon Neptune）——**这是"策略执行"在商业侧已被验证可落地的证据** |
| **自动阈值必须能导出为声明式配置** | Bigeye | 任何自动推断出的配置都要能导出成文件，否则用户不敢用（对应我们的"治理即代码"） |
| **主动承认血缘边界** | 华为云 DataArts | 官方把血缘约束单列成文档——**把"什么情况下血缘会不准"写清楚，比宣称"血缘全覆盖"更能赢得信任** |
| **治理成果推回业务工作面** | Alation（Connected Sheets） | 可信数据直接出现在 Sheets 等业务用户日常界面；**不要要求业务用户"来治理平台看一下"**（对应 `14` §5 的嵌入策略） |

## 6. 商业强、开源弱的 7 个点 → 我们的主战场

> 与 §6.1 的"开源生态空白点"互为印证：本节讲"能力差距在哪"，§6.1 讲"这些差距里哪些是真正无人占据的产品机会"。

1. **策略执行到数据面**（行过滤/列掩码/云原生策略/BI 可见性）——开源几乎空白，商业只有少数厂商做到，是最高价值的差异化。
2. **访问申请与审批闭环**（含到期回收与最小权限复盘）——开源普遍缺失。
3. **治理运营度量与记分卡**（把治理变成可考核、可分配的工作）——开源止于覆盖率统计。
4. **合规证据链**（审计报告、DSAR、保留策略）——开源基本没有。
5. **开箱 AI**（自动描述/分类/映射）——开源零散且不可审计。
6. **跨平台的列级血缘闭环**（含 BI 字段级贯通）——连 DataHub 都有已知缺口。
7. **企业级运维体验**（升级不痛、可回滚、有诊断包、有 SLO）——开源普遍是"部署容易、升级要命"。

---

### 6.1 开源生态的 10 个空白点，以及我们占据哪几个

`research/05` §11 系统盘点了开源生态的空白。把它与本方案的差异化对照（**这是"自研值不值"的最直接答案**）：

| # | 开源空白点 | 我们是否覆盖 | 对应设计 |
|---|---|---|---|
| 1 | **跨引擎策略下发与执行闭环**（授权引擎只解决 PDP；没有任何开源项目能把一份策略一致地下发到 Trino + Spark + 数仓 + BI 并证明执行了） | ✅ **核心主张** | `ADR-008`、`09` §9.7 |
| 2 | **契约的运行时强制**（格式已统一，但只有 CI/构建期/事后定时；**没有引擎中立的查询网关能按契约拒绝/隔离/改写查询**） | ✅ 覆盖前半（策略编译下发），后半（查询网关）作为可选扩展 | `09` §9.5、§9.7 |
| 3 | **可信度感知的血缘**（无人能回答"这条血缘可信度多少、覆盖了多少作业"；置信度加权血缘尚无标准） | ✅ **我们的差异化** | `ADR-004`、`09` §9.2 |
| 4 | **治理语义的统一本体**（分类 → 术语 → 策略 → 执行 端到端） | ✅ | `08` 全篇 |
| 5 | **访问的请求-审批-授权-回收工作流**（开源授权引擎只有 PDP，**没有 PAP/PIP**：申请、审批、时限、定期复核、审计报告） | ✅ **核心主张** | `09` §9.7 |
| 6 | 元数据变更的影响面分析 + 变更管理工作流闭环 | ✅ | `09` §9.2 影响分析 + §9.5 CI 门禁 |
| 7 | AI/Agent 的**上下文治理**（Agent 取数时的权限、血统、可信度与审计——2026 最前瞻的空白） | 🟡 部分（MCP + 工具级授权 + 审计），未做成独立产品 | `13` §6 |
| 8 | 引擎无关的异常检测 + 一等公民告警 | 🟡 部分（P2 起） | `09` §9.4 |
| 9 | 跨引擎统一的质量指标时间序列 + SLO | 🟡 部分 | `09` §9.4/§9.8 |
| 10 | 多租户 + 数据网格下的治理边界建模 | 🟡 部分（域/数据产品建模有，多租户语义待拍板） | `07` §9 Q2、`12` Q2 |

**结论**：我们明确占据 **1、3、4、5、6** 五个空白点，其中 **1 和 5 是开源生态中最大、最值钱的两块空缺**；**3 是唯一"行业公认痛点 + 无开源方案 + 技术可实现"的空白**。这三条构成了本方案的核心价值主张——如果这三条也不被业务认可，就应该二开而不是自研。



## 7. 开源强、商业弱的 3 个点 → 我们要保住的

1. **开放与可扩展**（自定义模型、插件、开放 API、无锁定）——商业产品普遍在 API 边界上设限。
2. **私有化与可控成本**（无按资产计费的规模惩罚）。
3. **多源血缘汇聚的实用主义**（社区连接器生态使广度增长快）。

## 8. 反面教训（明确不抄）

| 不抄 | 来源 | 原因 |
|---|---|---|
| Kafka 作为硬依赖 | DataHub | 小团队落地门槛过高；用 outbox 降级为可选 |
| 三处存储平级双写 | DataHub | 一致性漂移 + `restore-indices` 兜底是运维债 |
| 月更式破坏性变更 | OpenMetadata | 企业升级负担过重；我们要"兼容性承诺 + 三段式废弃" |
| 采集端与服务端强版本对齐 | OpenMetadata | 分布式部署下的现实灾难 |
| 血缘静默失败返回空 | OpenMetadata（issue 反映） | 用户无法区分"没有血缘"与"解析失败"，摧毁信任 |
| 扩展需改源码 + 重部署 | DataHub（PDL） | 业务方无法自助扩展 |
| 台账式治理报表 | 多数传统产品 | 报表不会自己完成治理，必须有待办与责任人 |
| AI 直接写元数据 | 部分新产品 | 无审计的 AI 元数据比空元数据更危险 |
| 大而全的首次交付 | 全部 | 治理平台必须"以灯塔域验证后再铺开" |

## 9. 结论

1. **开源解决"有没有"，商业解决"管不管得住"。** 我们的定位是在开源的成本结构下，做出商业产品的"管控与运营"能力。
2. **唯一值得自研的护城河**：元数据内核（模型/血缘可信度/事件机制）+ 策略执行到数据面 + 治理运营闭环 + 可审计 AI。其余一律复用生态件。
3. **抄架构不如抄取舍**：DataHub 的事件模型要抄，但其存储与运维取舍要改；OM 的模型统一性要抄，但其升级与采集耦合要改；商业产品的流程与度量要抄，但其封闭与价格不能抄。
